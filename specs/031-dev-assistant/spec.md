Документ отвечает на вопросы «что» и «зачем». Как это строится — в

## 2. Что говорит лекция недели 7

Заключительная неделя — собрать изученное (RAG, MCP, пайплайны, субагенты) в
полезный продукт под реальную задачу, а не в демо. Из лекции в этот день
берётся:
- **реестр инструментов**: модель видит имя и описание инструмента, исполнитель
  вызывает его и возвращает результат; **опасные операции** (удаление, `git
  push`, конфиги) — только с подтверждения человека;
- **пайплайн надёжен, модель — нет**: повторы, таймауты, запасная модель,
  детерминированные проверки, понятная точка для человека; сбой не прячется
  в журнал;
- **метрики**: задержка (p50/p95), токены и стоимость, качество (оценка
  человека, эталонные примеры), доля успешных прогонов;
- **проверка до «продакшена»**: эталонные примеры, сравнение версий, smoke.

Лектор называет задачу **Дня 32 — ревью PR**: diff, документация через RAG,
комментарий модели. Поэтому ассистент Дня 31 строится так, чтобы День 32
взял готовыми индекс документов проекта и git через MCP (включая diff).

## 4. Что уже есть и чего не хватает

**Есть (День 30):**
- `agent/rag/` — извлечение `.md` (по заголовкам) и `.py` (по `def`/`class`),
  разбиение «структура», эмбеддер bge-m3 в Ollama, поиск с реранкером,
  ответ с цитатами и проверкой цитат кодом, «не знаю» по порогу;
  `Индексатор(документы=…, индекс=…)` принимает свои каталоги;
- `agent/mcp/` — клиент MCP 2.x, `mcp-servers.json`, фильтр инструментов,
  признак «меняет» (заявка на подтверждение), цикл вызова инструментов
  моделью в `MemoryAgent`;
- мини-чат (`--чат`, `--реплика`, страница `/chat`) с командами `/память`,
  `/история`, `/новый`, `/выход`;
- приватный сервис (`service.py`, ключи с правами, лимиты, очередь, журнал без
  текстов) и Telegram-бот — клиент сервиса (`/doc` под маской ПД);
- каталог моделей, переключение «облако / локально», офлайн-предохранитель.

**Не хватает:**
- понятия «проект» (путь, что индексировать, свой индекс) и индексации по
  спискам «включить / исключить»;
- роли и шаблона ответа для документации разработчика — нынешние прошиты под
  договоры связи общества;
- git-сервера MCP;
- команды `/help вопрос` с маршрутом «документы + git»: мини-чат инструменты
  не вызывает;
- ручки сервиса для бота и права ключа на неё;
- проверок, показа и документов дня.

## 6. Требования

### 6.1 Функциональные

- **FR-01. Проект.** Файл `projects.json` описывает проекты: имя, путь,
  списки «включить» и «исключить» (шаблоны путей), каталог индекса, описание.
  Проект по умолчанию — `crm`. Путь проверяется: это каталог с репозиторием git.
- **FR-02. Индекс проекта.** `cli.py --проект-индекс [ИМЯ]` строит отдельный
  индекс проекта (стратегия «структура», bge-m3 локально) **только** из файлов
  под git (`git ls-files`), прошедших «включить / исключить». Индекс лежит вне
  репозитория (`index-projects/<имя>/`). Повторный запуск переиндексирует
  только изменённые файлы (по хэшу содержимого). Итог: число файлов, фрагментов,
  время, что пропущено и почему.
- **FR-03. ПД до индекса — точный профиль.** Перед разбиением текст проходит
  маску ПД **точного профиля** (`pd.скрыть(текст, профиль="точный")`): фамилии
  из локального `pd-names.txt` целым словом в любом регистре, e-mail, телефоны
  в телефонном написании (не цифры внутри хэшей), инициалы с фамилией только
  кириллицей («А.В. Фамилия», «Фамилия А.В.»). Полный профиль Дня 30
  (латинские двойники, инициалы в любом написании) на технической документации
  портит текст — `ORM`, `MVP`, `IP`, `POST`, `BODY.PEEK` (ворота 0) — и
  остаётся для `/doc` и договоров. Во фрагменты индекса, а значит и в модель,
  ПД не попадают. Итог индексации сообщает, сколько и каких замен было (без
  самих значений). Тот же точный профиль — на выходе `/help` во всех каналах,
  включая Telegram.
- **FR-04. git-сервер MCP.** `git_server.py` (stdio, SDK `mcp` 2.x) с
  инструментами только на чтение: `git_branch` (текущая ветка и коммит),
  `git_status` (короткий статус), `git_ls_files` (список файлов по шаблону, с
  пределом), `git_diff` (рабочий каталог или между двумя ссылками, с пределом
  размера), `git_log` (последние N коммитов), `git_show` (текст файла из
  коммита, до 20 000 символов — версия 2: без него ассистент не мог посчитать
  принципы конституции по фрагментам). Корень проекта задаётся при
  запуске; пути вне корня отвергаются; команды, меняющие репозиторий или
  ходящие в сеть, в сервере **отсутствуют**. git вызывается так, чтобы не
  писать даже служебные файлы (`GIT_OPTIONAL_LOCKS=0`).
- **FR-05. Регистрация сервера.** `mcp-servers.json` получает сервер `git`
  с пометкой «только чтение»; фильтр инструментов и офлайн-режим действуют как
  на остальные серверы. В списке `--mcp` сервер виден с инструментами.
- **FR-06. Ассистент.** Модуль ассистента отвечает на вопрос о проекте:
  1. код через MCP берёт ветку и короткий статус;
  2. поиск по индексу проекта (с реранкером), ответ с источниками
     (файл, раздел) и цитатами, цитаты проверяет код;
  3. модели доступны инструменты `git_ls_files`, `git_diff`, `git_log`; она
     вызывает их, когда вопрос о файлах, изменениях или истории (не более
     заданного числа кругов);
  4. если в документах ответа нет и инструменты не помогли — «не знаю» и
     уточнение, а не выдумка.
  В ответе видно: ответ, источники, цитаты с проверкой, ветка, какие
  инструменты вызывались и с какими аргументами, модель, токены, время.
- **FR-07. Роль ассистента.** Роль и шаблон ответа — «ассистент разработчика
  проекта <описание проекта>», отдельно от роли «договоры связи». Прежний путь
  ответов по документам организации не меняется.
- **FR-08. `/help` в консоли.** В мини-чате (`--чат`) и в `--реплика`:
  `/help вопрос` — ответ ассистента; `/help` без вопроса — список команд чата
  с примером `/help`. Модель — та, что выбрана в чате (`--модель`), облачная
  или локальная. Ответ ассистента в историю чата пишется как отдельный ход.
- **FR-09. `/help` в вебе.** На странице `/chat` то же самое: `/help вопрос`
  даёт ответ ассистента с источниками, цитатами, веткой и вызовами
  инструментов; модель — из выбора на странице; работает и с потоком (события
  «готово» / «ошибка»). Паритет с консолью.
- **FR-10. Ручка сервиса.** `POST /v1/project/help` (`{"question": …}`) —
  ответ ассистента в JSON: ответ, источники, цитаты, ветка, вызовы
  инструментов, модель, `usage`, время. Право ключа — новое «проект»; ключ,
  лимит запросов, предел тела, длина вопроса, очередь, таймаут, обрыв клиента,
  журнал без текстов — как у `/v1/documents/answer`.
- **FR-11. Модель сервиса для проекта.** В `service.json` — модель ручки
  проекта: `ds-flash` (облако) или `loc-rag-docs` (локально); переключается
  из консоли и со страницы `/admin` (ключ «админ») без перезапуска.
  Офлайн-предохранитель процесса сервиса пропускает наружу **только**
  `api.deepseek.com` (разрешение задаётся при запуске всегда); вызвать
  облачную модель может только ассистент ручки проекта и только при
  переключателе «облако» — это обеспечивает код и проверяют тесты и журнал
  сети. `/v1/chat/completions` и `/v1/documents/answer` остаются локальными.
- **FR-12. Запасной путь.** Облачная модель не ответила (сеть, 5xx, таймаут,
  неразборчивый ответ) — один повтор, затем ответ локальной моделью с пометкой
  «облако недоступно — ответила локальная модель». Отказ git-сервера — ответ по
  документам с пометкой «git недоступен». Сбой виден в ответе и в журнале, а
  не только в журнале.
- **FR-13. `/help` в Telegram.** `/help` без текста — прежняя мгновенная
  справка (дополнена строкой про `/help вопрос`). `/help вопрос` — в очередь
  чата (не мгновенно), запрос в `/v1/project/help` ключом бота, ход ответа
  правками («ищу в документах проекта… N с»), повторы при 429 как у `/doc`,
  ответ под маской ПД. Ключ бота получает право «проект»
  (`--телеграм-ключ`).
- **FR-14. Метрики.** Каждый ответ ассистента (консоль, веб, сервис) пишет в
  журнал строку **без текстов**: канал, проект, модель, запасной путь,
  вызовы инструментов (имена), «не знаю», токены входа и ответа, время по
  этапам, итог. `cli.py --помощь-метрики` показывает число ответов, долю «не
  знаю», долю запасного пути, p50/p95 времени, токены на ответ — по моделям и
  каналам.
- **FR-15. Службы Дня 31.** `day31-llm` и `day31-tg` вместо `day30-*`: те же
  порты (8443), та же память сервиса (ключи, сертификаты, центр
  сертификации, журнал — перенесены из Дня 30), тот же токен бота. Службы Дня
  30 останавливаются и выключаются из автозапуска, их файлы не удаляются.
  Телефон владельца и его ключи продолжают работать.

### 6.2 Нефункциональные

- **NFR-01. Только чтение CRM.** Ни один процесс дня не пишет в каталог CRM и
  в её `.git`. Над CRM работает другая сессия, поэтому «CRM не изменилась за
  день» не доказательство; доказательство — (а) git вызывается только из белого
  списка подкоманд на чтение с `GIT_OPTIONAL_LOCKS=0` и
  `GIT_TERMINAL_PROMPT=0` (тесты), (б) **короткое окно**: полный набор
  инструментов git-сервера и индексация прогоняются, а mtime `.git/index`,
  `HEAD` и `git status --porcelain` CRM сравниваются сразу до и сразу после
  (секунды–минуты); если `HEAD` сдвинулся внутри окна — коммит другой сессии,
  окно повторяется. Индекс, журналы, кэш — в каталоге Дня 31.
- **NFR-02. ПД.** В индексе, ответах, журналах, отчётах, видео и коммитах —
  нет фамилий из `pd-names.txt`, e-mail, телефонов; маска точного профиля до
  индекса и на выходе; полный профиль — проверочный скан фрагментов индекса
  (находки сверяются глазами: ложные срабатывания на латинице допустимы,
  настоящие ПД — нет).
- **NFR-03. Сеть.** Агент и бот — как в Дне 30. Сервис: внешний хост только
  `api.deepseek.com` и только во время запросов к ручке проекта в режиме
  «облако»; в режиме «локально» — внешних 0.
- **NFR-04. Время.** Ответ на `/help` облачной моделью — до 30 с на этой
  машине (поиск с реранкером — локально), локальной — минуты (показывается
  ход).
- **NFR-05. Деньги.** Вызовы ds-flash — центы за прогон; другие платные
  сервисы не используются.
