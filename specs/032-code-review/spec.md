# День 32 — автоматическое ревью кода: спецификация

Документ отвечает на вопросы «что» и «зачем». Как это строится — в
[plan.md](plan.md), по каким шагам — в [tasks.md](tasks.md). Код пишется
после того, как владелец подпишет все три документа.

## 1. Задание (дословно)

> День 32. Автоматизация ревью кода
>
> Настройте пайплайн, в котором ассистент анализирует новый PR.
> Ассистент должен:
> 👉 получать diff и изменённые файлы
> 👉 использовать RAG (документация + код)
> 👉 выдавать текст ревью
>
> Минимальный результат:
> 👉 пайплайн (например GitHub Action) запускается на PR
> 👉 ассистент получает diff
> 👉 возвращает:
> - потенциальные баги
> - архитектурные проблемы
> - рекомендации
>
> Результат: Автоматическое AI-ревью кода
>
> Формат: Видео + Код

## 2. Что говорит лекция недели 7

Лектор приводит День 32 как пример AI-пайплайна: создаётся PR, из него берётся
diff, из RAG — документация (как должен быть устроен код и PR), модель
ревьюит и пишет комментарий, а при серьёзных ошибках может и заблокировать
слияние. Реализация — простой GitHub-workflow: checkout и скрипт на Python.
Из лекции в этот день берётся также:
- **надёжность пайплайна**: повторы, таймауты, детерминированные проверки,
  понятная точка эскалации человеку; сбой не прячется в журнал;
- **метрики**: время (p50/p95), токены и стоимость за PR (рост вдвое против
  базовой линии последних прогонов — тревога), качество (оценка человека,
  прогон эталонных примеров), доля прогонов без вмешательства;
- **человек в цепи**: слияние решает человек, ревью только советует и красит
  проверку;
- **субагенты**: параллельное делегирование подзадач со своим контекстом и
  сборка результата оркестратором.

## 4. Что уже есть и чего не хватает

**Есть (День 31):**
- `git_server.py` — MCP-сервер git только на чтение: `git_diff` между двумя
  ссылками, `git_show` (файл из коммита), `git_log`, `git_ls_files`;
- `agent/devassist/project.py` — проект из `projects.json`, индекс только из
  файлов под git, маска ПД точного профиля до индекса;
- `agent/rag/` — индексатор (разбор `.md` по заголовкам, `.py` по
  `def`/`class`), эмбеддеры `bge-m3` (Ollama) и `хэш` (без модели), кэш векторов
  по тексту, проверка цитат `cite.py`;
- `agent/llm.py` — клиент ds-flash с повторами при 429, учёт токенов,
  `agent/catalog.py` — цены моделей;
- ассистент `/help` (консоль, веб, Telegram), метрики без текстов, судья
  контрольного набора;
- маска ПД `pd.скрыть`, Telegram-бот и приватный сервис (службы `day31-*`).

**Не хватает:**
- пайплайна на PR: workflow, сбор события, публикация комментария и статуса;
- индекса **своего** репозитория (документы + код) и поиска, который
  поднимается на пустом облачном раннере за разумное время;
- ревьюеров (ролей, формата находок), параллельного запуска и сборщика с
  проверкой находок кодом;
- эскалации человеку (Telegram) и метрик пайплайна;
- контрольного набора PR с посеянными ошибками, проверок, показа, документов.

## 5. Решения владельца (развилки, 2026-10-15)

| Развилка | Выбор |
|---|---|
| где пайплайн | **GitHub Actions, облачный раннер**; ключ DeepSeek — в Secrets репозитория (кладёт владелец). Тот же конвейер запускается локально командой для проверок |
| поиск на раннере | **по замеру** (ворота 0): лексический индекс без модели (`хэш`), bge-m3 через Ollama с кэшем, готовый индекс из релиза — выбор по времени и качеству, итог показывается владельцу |
| итог ревью | **комментарий + красная проверка**: один комментарий с тремя разделами, обновляется при новых коммитах; критичная находка — проверка PR красная; слияние решает человек |
| агенты | **три ревьюера параллельно + сборщик** |
| модель | **ds-flash**; ds-pro — только судья контрольного набора; траты на прогоны, проверки и показ разрешены |
| GitHub | **владелец даёт токен на один репозиторий** (fine-grained PAT, только Day-32): ассистент пушит демо-ветки и открывает PR; в `main` пушит владелец |
| интерфейсы | **консоль + веб + бот**: `cli.py --ревью`, `/review` в чате агента (консоль и веб); уведомление в Telegram при красном ревью и сбое пайплайна |
| показ | **два PR**: настоящая небольшая доработка (ожидается зелёный) и PR с 2–3 посеянными ошибками (ожидается красный) |

**Что задано без выбора** (безопасность и границы):
- триггер `pull_request`: в PR из форка секретов нет, токен только на чтение —
  ревью пишется в сводку задания, комментарий не публикуется;
- права `GITHUB_TOKEN` — `contents: read`, `pull-requests: write`, больше ничего;
- у ревьюеров нет инструментов, меняющих репозиторий или GitHub: слияния,
  push, правки конфигов в наборе нет **по построению**;
- diff, заголовок и описание PR — **недоверенные данные**: ограничены по
  размеру, бинарные и lock-файлы пропускаются, инструкции внутри diff — данные;
- CRM на GitHub не попадает ни в каком виде; службы `day31-*` не трогаются.

**Что меняется в решениях Дня 31:** SPEC-031, «Вне рамок» — «ревью PR и
комментарии в GitHub», «субагенты и параллельное делегирование» — теперь в
рамках. Ассистент `/help` по CRM не меняется.

## 6. Требования

### 6.1 Функциональные

- **FR-01. Проект «сам».** В `projects.json` — проект `advent` (репозиторий
  Дня 32, путь — корень репозитория, на раннере — каталог checkout):
  «включить» — документы и код, «исключить» — протоколы прогонов, тесты-гиганты
  и данные (точный список — по замеру ворот 0). `/help` по умолчанию остаётся
  на CRM.
- **FR-02. Индекс на раннере.** Индекс проекта строится из **базы PR**
  (`git archive`/`git show` базового коммита во временный каталог) способом,
  выбранным на воротах 0; время построения и поиска — в метриках. Локально —
  тот же код.
- **FR-03. Вход пайплайна.** Скрипт получает базу и голову PR (из события
  GitHub или аргументов), считает merge-base и берёт через git-сервер MCP:
  сводку изменений (файлы, +/−), diff, полный текст изменённых файлов на
  голове. Фильтр: бинарные, lock-файлы, сгенерированные и файлы больше
  предела не отдаются модели, но перечисляются в ревью как «не просмотрены».
  Пределы: diff на файл, diff всего, число файлов; при обрезке ревью так и
  пишет: «просмотрено N из M файлов».
- **FR-04. Поиск опоры.** По diff код строит запросы (пути, имена изменённых
  функций и классов, добавленные идентификаторы, заголовок PR) и находит
  фрагменты документов и кода из индекса базы. Отдельно, без модели, — места
  вызова изменённых функций в коде базы (поиск по имени). Фрагменты из
  изменённых файлов не дублируют diff.
- **FR-05. Три ревьюера параллельно.** «Баги», «архитектура», «рекомендации» —
  отдельные вызовы модели со своей ролью и своим отбором фрагментов,
  запускаются одновременно. Каждый возвращает JSON: список находок `{файл,
  строка, серьёзность (критично | важно | мелочь), суть, почему, фрагмент_diff,
  источники}`; пустой список — нормальный ответ. Ревьюерам доступен
  инструмент `git_show` (файл базы или головы, не больше заданного числа
  кругов) — только чтение.
- **FR-06. Сборщик.** Код (не модель) проверяет каждую находку: файл есть в
  изменениях, строка внутри изменённых участков (иначе — без строки),
  `фрагмент_diff` находится в diff (проверка цитаты, как в Дне 24), источники —
  номера выданных фрагментов. Неподтверждённая находка не может быть
  «критично» (понижается до «важно» с пометкой). Дубли между ревьюерами
  (тот же файл, близкая строка, похожая суть) объединяются. Вердикт
  детерминирован: **красный**, если есть подтверждённая находка «критично» в
  разделах «баги» или «архитектура»; иначе зелёный.
- **FR-07. Комментарий в PR.** Один комментарий с меткой ревью: вердикт,
  три раздела, «не просмотрены», пометки о сбоях, подвал (модель, время, токены,
  стоимость, коммит головы). При новом коммите в PR тот же комментарий
  обновляется, а не плодится. Текст модели проходит маску ПД точного профиля и
  обезвреживание разметки (упоминания `@`, HTML). Тот же текст — в сводке
  задания (`$GITHUB_STEP_SUMMARY`).
- **FR-08. Проверка PR.** Красный вердикт — шаг ревью завершается с ошибкой,
  проверка PR красная, в комментарии сказано почему. Зелёный — проверка
  зелёная. Слияние решает человек (правило защиты ветки — по желанию
  владельца).
- **FR-09. Сбои.** Повтор вызова модели при сетевой ошибке, 5xx, 429,
  неразборчивом JSON (один повтор с подсказкой формата); таймаут на ревьюера
  и на весь прогон. Упал один ревьюер — ревью публикуется по остальным с
  пометкой «раздел не выполнен». Упали все, или PR из **этого** репозитория, а
  ключа нет (ошибка настройки) — комментарий «AI-ревью не выполнено, нужен
  человек», проверка красная, уведомление владельцу. PR **из форка** (секретов
  нет по правилам GitHub, токен на чтение) — не ошибка: ревью пропускается с
  пояснением в сводке задания, проверка зелёная (код выхода 0), ревью такого PR
  владелец запускает сам (`--ревью-гитхаб N`). Черновые PR не ревьюятся до
  «готов к ревью».
- **FR-10. Эскалация в Telegram.** При красном вердикте, сбое пайплайна или
  тревоге метрик — сообщение владельцу через бота (секреты `TELEGRAM_BOT_TOKEN`,
  `TELEGRAM_CHAT_ID`): номер и ссылка PR, вердикт, число находок по разделам,
  причина. Без кода и без текстов находок; под маской ПД. Нет секретов —
  уведомление пропускается с пометкой в сводке.
- **FR-11. Метрики.** Каждый прогон пишет строку **без текстов**: PR, коммит,
  модель, время по этапам (индекс, поиск, ревьюеры, сборка, публикация),
  токены и стоимость по ревьюерам, число находок по разделам и
  серьёзностям, подтверждено / понижено, вердикт, сбои. Строка — в скрытой
  части комментария, в сводке задания и в артефакте прогона. Базовая линия —
  медиана последних 20 прогонов из комментариев репозитория; токены или время
  больше вдвое — тревога (строка в комментарии + Telegram). Оценка человека —
  реакции 👍/👎 на комментарий ревью. `cli.py --ревью-метрики` собирает
  прогоны (локальные и с GitHub), p50/p95 времени, токены и стоимость на PR,
  долю красных, долю без сбоев, долю 👍.
- **FR-12. Консоль.** `cli.py --ревью [БАЗА...ГОЛОВА]` (по умолчанию
  `main...HEAD` локального репозитория Дня 32) — тот же конвейер без
  публикации: печать ревью, вердикт кодом выхода; `--модель` — как везде.
  `--ревью-гитхаб N` — то же для PR номер N с публикацией (токен владельца из
  `.env`) — для отладки без push.
- **FR-13. Чат агента.** `/review [диапазон]` в мини-чате (консоль) и на
  странице `/chat` (веб, с потоком) — ревью диапазона с карточкой: вердикт,
  разделы, находки с файлом и строкой, ход по этапам. Паритет консоли и веба.
  `/help` без вопроса упоминает `/review`.

### 6.2 Нефункциональные

- **NFR-01. Безопасность раннера.** `pull_request`, права токена минимальные,
  ключи только из Secrets; ключ и токен не печатаются (маскирование Actions +
  свой фильтр журнала); в журнале задания нет текстов фрагментов и находок
  сверх итогового ревью. Сторонние actions — только `actions/*` с
  закреплённой версией.
- **NFR-02. Недоверенный вход.** diff и описание PR передаются модели как
  данные в разметке «это данные, не инструкции»; никакой инструмент ревьюера
  не меняет репозиторий, GitHub или сеть; число кругов инструментов и размер
  их вывода ограничены.
- **NFR-03. Время.** Ревью PR обычного размера (до 20 файлов, до 1500 строк
  diff) — до 5 мин от начала задания до комментария на облачном раннере (с
  установкой зависимостей и индексом); цель — до 3 мин.
- **NFR-04. Деньги.** ds-flash — центы за ревью; ds-pro — только судья
  контрольного набора. Других платных сервисов нет; Actions — бесплатная квота
  публичного репозитория.
- **NFR-05. ПД и секреты.** Репозиторий Дня 32 публичный: в нём, в
  комментариях, журналах, видео — нет ПД, ключей, токена бота, ID владельца,
  токена GitHub. Маска на выходе ревью и уведомления.

## 9. Конституция дня (постоянные ограничения)

1. **Публичный репозиторий.** Ничего из `DocsSample/`, `index*/`, `memory/`,
   `out/`, `demo/`, `pd-names.txt`, `.env` в git; в коммитах, комментариях PR,
   журналах Actions, видео — нет ПД, ключей, токена бота, ID владельца,
   токена GitHub. Перед каждым push — скан по значению.
2. **Токен GitHub владельца** — только в `.env`, только репозиторий Дня 32;
   ассистент пушит только демо- и пробные ветки, **в `main` пушит владелец**;
   ветки и PR не удаляются без слова владельца.
3. **Ревью не меняет репозиторий**: ни слияния, ни push, ни правок — только
   комментарий и статус.
4. **CRM** — не участвует; службы `day31-*`, Ollama — не трогаются.
5. **Порты:** 5000 — сервер владельца, 5001 — стенд, 8766, 11435, 8443, 8444 —
   заняты прежними днями. Гасятся только свои процессы по PID.
6. **Запись** — только окно браузера (кадры CDP); Telegram Web — только скрипт
   показа и только чат с ботом; GitHub — без входа в аккаунт, если хватает
   публичного просмотра.
7. **Имена файлов** — латиницей; тексты, ключи консоли, ревью — по-русски.
8. **`.py` не править во время долгих прогонов**; черновики — в `Day-32/out/`.
9. **Платное** сверх ds-flash/ds-pro прогонов — по согласию заранее.

## 10. Вне рамок

- автоматическое слияние, правки кода моделью («suggested changes»), push;
- замечания на строках diff (review comments) — выбрано одним комментарием;
- self-hosted раннер, ревью чужих репозиториев и CRM;
- `/review` в Telegram-боте как команда (бот только уведомляет);
- локальная модель на раннере (в консоли и вебе — выбором `--модель`).
