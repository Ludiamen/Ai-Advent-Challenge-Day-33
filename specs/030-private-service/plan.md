# День 30 — локальная LLM как приватный сервис: план

Как строится то, что описано в [spec.md](spec.md). Шаги — в [tasks.md](tasks.md).

## 1. Архитектура

```
 телефон (Wi-Fi 192.168.1.x)     клиент в Docker (172.x, свой CA)     браузер ноутбука (видео)
            │  HTTPS :8443               │  HTTPS :8443                       │
            └──────────────┬─────────────┴────────────────────────────────────┘
                           ▼
 service.py ── uvicorn + TLS (свой центр сертификации) ── служба systemd --user «day30-llm»
   │  1. подсеть клиента в списке?            нет → 403
   │  2. ключ API (хэш) и его права           нет → 401 / 403
   │  3. лимит ключа (ведро, R в минуту)      сверх → 429 rate_limited + Retry-After
   │  4. тело ≤ 256 КБ; вход ≤ 3400 токенов   сверх → 413 (до вызова модели)
   │  5. очередь: 1 генерация, ждут ≤ N        сверх → 429 queue_full + Retry-After
   │  6. генерация:
   │       /v1/chat/completions ──► Ollama 127.0.0.1:11434 /api/chat (loc-rag-docs, think false, keep_alive)
   │       /v1/documents/answer ──► Отвечатель Дня 29 (поиск без LLM + loc-rag-docs) в потоке
   │  7. журнал: JSONL метаданных (без текстов); офлайн-предохранитель — внешних 0
   ├── /chat   страница чата (ключ — в вкладке)
   ├── /admin  страница сервиса (ключ «админ»): очередь, журнал с адресами, ресурсы, нагрузка
   └── /health без ключа
 service_load.py (в контейнере python:3.12-slim) ── ступени 1→2→4→8, повтор после 429
```

Ollama остаётся службой на 127.0.0.1 — наружу её не видно. Шлюз — отдельный от
`web.py` процесс: в нём нет инструментов MCP, трекера и памяти агента.

## 2. Решения

**D-01. Стек — FastAPI + uvicorn с TLS.** Асинхронный сервер держит ожидающих в
очереди, не занимая потоков, а `/health` и `/admin` отвечают во время
генерации (NFR-01). uvicorn и starlette уже стоят в `.venv` (через SDK MCP);
FastAPI добавляется в `requirements.txt` (A-7). OpenAPI-схема — по
`/openapi.json`; страница Swagger не подключается (её скрипты грузятся из CDN,
а сервис приватный).

**D-02. Код — пакет `agent/service/` и вход `service.py`.**
`config.py` (настройки `service.json` + данные в `memory/service/`), `keys.py`,
`limits.py` (ведро, очередь), `tokens.py`, `certs.py`, `journal.py`,
`gateway.py` (приложение), `unit.py` (служба systemd), `load.py` (сводка
нагрузки). `service_load.py` — отдельный файл без зависимостей проекта (только
httpx и стандартная библиотека), чтобы запускаться в чистом контейнере.

**D-03. Настройки и данные.** `service.json` в репозитории — значения по
умолчанию (порт 8443, подсети, лимиты, модель). Ключи (`keys.json` — только
хэши), журнал запросов, сертификаты и их закрытые ключи — в
`memory/service/` (в `.gitignore`).

**D-04. Ключи.** `sk-day30-` + 32 случайных байта (base64url); на диске —
sha256 ключа (ключ случайный и длинный — соль не нужна), сравнение
`hmac.compare_digest`. Права — набор из `чат`, `документы`, `админ`. Ключ
передаётся заголовком `Authorization: Bearer …` (как у OpenAI). Отозванный
ключ — 401.

**D-05. Подсети — до ключа.** Проверка адреса клиента (`ipaddress`) идёт первой:
чужая подсеть получает 403, даже не узнав, верен ли ключ. Заголовки
`X-Forwarded-For` не учитываются: прокси перед сервисом нет.

**D-06. HTTPS — свой центр сертификации.** `openssl`: ключ и сертификат центра
(`ca.crt`) и сертификат сервера с SAN `IP:127.0.0.1`, `IP:<адрес в домашней
сети>`, `IP:172.17.0.1`, `DNS:localhost`, `DNS:host.docker.internal` — если
Docker не достанет до адреса в домашней сети (A-2), перевыпускать не придётся. Сменился адрес (DHCP) — `--сервис-сертификат` выпускает
новый сертификат сервера тем же центром. Клиент в Docker получает `ca.crt` и
проверяет сертификат. Телефон: один раз принять предупреждение или поставить
`ca.crt` (инструкция в MANUAL-CHECK).

**D-07. Очередь — явная, FIFO.** Одно место генерации (`asyncio`-замок) и
счётчик ждущих. Если ждущих уже N — сразу 429 `queue_full`; `Retry-After` =
средняя длительность генерации × (ждущих + 1), округление вверх. Клиенту без
потока — заголовки `X-Queue-Position` и `X-Queue-Wait`; в потоке — комментарий
SSE `: очередь N` до первого куска (клиенты OpenAI комментарии пропускают).
Чат и документы стоят в одной очереди: модель одна.

**D-08. Лимит запросов — ведро на ключ.** Ёмкость R, пополнение R/60 в секунду
(по умолчанию R = 6). Проверяется после ключа, до очереди. Отказ — 429
`rate_limited`, `Retry-After` — до следующего жетона.

**D-09. Токены — токенизатор самой модели (A-1).** Первый путь —
`llama-cpp-python`: `Llama(model_path=<блоб GGUF>, vocab_only=True).tokenize()`
— тот же код словаря и пре-токенизатора, что у раннера Ollama, веса не
грузятся (сборка из исходников: `gcc` есть, `cmake` придёт с pip). Второй —
`gguf` + `tokenizers` (`tokenizers` уже стоит). Шаблон чата не угадывается, а
измеряется: 1, 2 и 3 сообщения → `prompt_eval_count` → константы «префикс + на
сообщение» в `tokens.py` (`prompt_eval_count` не зависит от кэша промпта —
День 28, сверка честная и на тёплой модели). Если точно не выйдет — оценка по
длине с худшим измеренным отношением и запасом (spec, A-1). Предел входа — 3400
токенов (окно 4096 − ответ 600 − запас 96).
**Ворота 0:** путь `llama-cpp-python` подтвердился — словарь за 0,8 с, шаблон
`<|im_start|>роль\nтекст<|im_end|>\n` × N + `<|im_start|>assistant\n<think>\n\n</think>\n\n`;
7 коротких входов — точно, длинный — +1 (счёт не меньше настоящего). Пакет
собирается из исходников (≈ 10 мин, нужен `gcc`) — это пишется в README; в
тестах токенизатор подменяется.

**D-10. Прокси к Ollama — `/api/chat` (A-4).** OpenAI-совместимая ручка Ollama
(`/v1/chat/completions`) не принимает `keep_alive`, `think` и `options`, а
модель без них выгружалась бы через 5 минут простоя, и ответ уходил бы в
«размышления». Поэтому шлюз шлёт в `/api/chat` то же, что агент
(`llm.ollama_payload`): `think: false`, `keep_alive`, `num_ctx` 4096,
`num_predict` ≤ 600, `temperature` клиента. Ответ собирается в формат OpenAI
(≈ 40 строк): `chat.completion` с `usage` из `prompt_eval_count`/`eval_count`
и `finish_reason` из `done_reason`; поток — куски `chat.completion.chunk` и
`data: [DONE]`. Закрыл клиент соединение — шлюз закрывает поток к Ollama, и
Ollama прерывает генерацию (ворота 0: после обрыва на 5-м куске из 400 следующий
запрос ответил за 5,2 с).

**D-11. Документы — `Отвечатель` Дня 29 в отдельном потоке (A-5).** Профиль
«локальный», модель `loc-rag-docs` с конфигурацией «после»; вызов —
`asyncio.to_thread` внутри места очереди. Ответ — JSON: текст, источники с
`chunk_id`, цитаты с проверкой, «не знаю» с уточнением, замеры.

**D-12. Приватность процесса.** Шлюз включает офлайн-режим Дня 27 при старте:
облако и внешние адреса блокируются предохранителем, журнал сети считает
запросы; `/admin` показывает «внешних N». Журнал запросов — JSONL метаданных
(FR-13), ротация по 5 МБ.

**D-13. Нагрузка — клиент в Docker.** `docker run --rm` образа
`python:3.12-slim` в сети Docker по умолчанию (172.17.0.0/16) с
примонтированными `service_load.py`, `ca.crt` и каталогом итогов; `pip install
httpx openai` внутри. Ступени 1, 2, 4, 8 клиентов, по 2 вопроса на клиента,
`max_tokens` 200; вопросы чата — 16+ разных общих (кэш промпта Ollama не
помогает), по документам — только из `local-opt.json → gpu.годные` (проверены
без ПД, День 29). У каждого клиента свой ключ `нагрузка-1…8` с правом «чат»
(«нагрузка-д1…д2» — «документы»): мерим очередь, а не лимит ключа. После 429 —
повтор по `Retry-After`; клиент пишет `finish_reason`. До и после каждой ступени клиент отмечает её на
сервере (`/admin/api/step`, ключ «админ»), и шлюз снимает пик памяти и CPU
раннера (`resources.Наблюдатель`, День 29). Модель держится в памяти
(`keep_alive`), как у живого сервиса; первая загрузка — отдельно. Итоги —
`index/service-load/run-*.json` и таблица на `/admin`.

**D-14. Служба — systemd пользователя.** `~/.config/systemd/user/day30-llm.service`:
`ExecStart=<.venv>/python service.py`, `Restart=on-failure`, `RestartSec=3`.
Без linger служба живёт, пока владелец в системе (A-6) — для домашнего
сервера это ограничение пишется в README. `--сервис установить` пишет файл
службы и делает `daemon-reload`; `старт|стоп|статус` — через `systemctl --user`.

**D-15. Страницы.** `/chat` и `/admin` — шаблоны в `templates/`, без внешних
скриптов. Ключ — в `sessionStorage` вкладки. `/admin` опрашивает
`/admin/api/state` раз в секунду: очередь (идёт, ждут), последние 50 запросов
(время, адрес, ключ, ручка, код, ожидание, длительность, токены), ресурсы,
итоги нагрузки; кнопки «нагрузка: ступень N» (запускают тот же
`service_load.py` в Docker, что и консоль).

**D-16. Проверка подсетей на живом сервисе.** Своя сеть Docker `day30-foreign`
(10.99.0.0/24 — не в списке): запрос из неё — 403; после проверки сеть
удаляется. Сети и контейнеры CRM не трогаются и в список подсетей не входят.

**D-17. Лимиты в проверках — дёшево.** Ведро считает все запросы ключа к
`/v1/*`, поэтому лимит проверяется семью быстрыми `/v1/models` за секунды.
Всплеск для `queue_full` — запросы с `max_tokens` 16 и промптом в одну строку.

**D-18. Данные сервиса — под `MEMORY_DIR`.** Ключи, журнал и сертификаты —
`$MEMORY_DIR/service/`, как остальная память агента: тесты и стенд пишут в
свои каталоги, а не в живые ключи. **Показ идёт по живой службе** на 8443 с
отдельными ключами показа (`показ-чат`, `показ-документы`, `показ-админ`,
отзываются после записи); браузерная регрессия `browser.mjs … сервис` — по
стенду на **8444** со своей памятью.

## 5. Проверки до прогонов (тесты пишутся раньше кода модуля)

- `КлючиСервиса` — создание (показ один раз), хэш на диске, права, отзыв,

- `ЛимитыСервиса` — ведро (время подменено), очередь: FIFO, N ждущих, отказ с

  предел и 413;
- `ШлюзOpenAI` — `TestClient` + подставной Ollama (`httpx.MockTransport`):
  модели, чат без потока и с потоком, ошибки в формате OpenAI, заголовки
  очереди и урезания, журнал без текстов;
- `ДокументыСервиса` — ручка документов на подставном отвечателе: права, формат;
- `СлужбаИСертификаты` — текст unit-файла, SAN сертификата (на временном центре);
- `НагрузкаСервиса` — сводка прогона: перцентили, ошибки против отказов;
- `КонсольИВебДня30` — ключи консоли и страницы.

## 6. Сценарий показа (черновик для `DEMO-CHROME.md`)

1. `/admin`: служба `day30-llm` активна, `https://192.168.1.43:8443`, модель
   `loc-rag-docs`, лимиты, ключи (имена и права), подсети; очередь пуста.
2. `/chat` с ключом «чат»: вопрос — ответ потоком; под ответом — ожидание,
   токены, время.
3. Режим «по документам» с ключом «документы»: ответ с источником и цитатой; с
   ключом «чат» — «нет права: документы» (403).
4. Лимиты: длинный текст — «вход 5200 токенов, предел 3400» (413); серия
   запросов — «лимит 6 в минуту, повторите через N с» (429).
5. Доступ по сети: журнал на `/admin` — запросы от 172.x (Docker) и
   192.168.1.x (телефон, заранее).
6. Нагрузка вживую: 8 клиентов по 1 запросу из Docker — «идёт 1, ждут 4,
   отказано 3 → повтор», ошибок 0 (в ускоренной копии ×8).
7. Итог ступеней 1→2→4→8: p50/p95, ожидание, пропускная способность, память и
   CPU раннера.

## 8. Порядок работ и ворота


план; A-2/A-3 — способ доказательства доступа по сети; A-4 — путь прокси.
