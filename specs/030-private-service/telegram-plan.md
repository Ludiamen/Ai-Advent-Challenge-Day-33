# День 30, дополнение — Telegram-чат: план

Как строится то, что описано в [telegram-spec.md](telegram-spec.md). Задачи —
[telegram-tasks.md](telegram-tasks.md).

## 1. Архитектура

```
 телефон / Telegram Web владельца
            │  (облако Telegram)
            ▼
 api.telegram.org ◄── long polling ── telegram_bot.py  (служба systemd --user «day30-tg»)
                                       agent/service/telegram.py
                                         Bot API (httpx): getUpdates, sendMessage,
                                           editMessageText, sendChatAction, getMe, leaveChat
                                         владелец? (Telegram ID из .env) ── нет → отказ раз в сутки
                                         updates по update_id: одно дело до конца
                                         история чата в памяти (N реплик), /new
                                         чат  ─► HTTPS 127.0.0.1:8443 /v1/chat/completions (поток)
                                         /doc ─► HTTPS 127.0.0.1:8443 /v1/documents/answer
                                                  └► agent/service/pd.py: маска ПД
                                         журнал бота (JSONL, без текстов), состояние для /admin
                                         офлайн-предохранитель: внешний — только api.telegram.org
                                       ▼
                            service.py (День 30, без изменений по смыслу):
                            ключ «телеграм» → лимит → 413 → очередь → loc-rag-docs
```

Бот — **ещё один клиент** сервиса, как контейнер Docker или телефон: всё, что
сервис умеет (лимиты, очередь, предел контекста, журнал без текстов), к нему
применяется само. Модель бот не вызывает; процесс сервиса остаётся в
офлайн-режиме с «внешних 0».

## 2. Решения

**D-T01. Бот — отдельный процесс и отдельная служба.** `telegram_bot.py` (вход)
и `agent/service/telegram.py` (логика). Отдельно — потому что боту нужен
интернет (Telegram), а сервису нельзя; и потому что падение бота или VPN не
должно задевать сервис. Служба `day30-tg.service` — тем же `unit.py`, с
`After=day30-llm.service`, `Restart=on-failure`, `RestartSec=10`.

**D-T02. Bot API — своим клиентом на `httpx`.** Нужно шесть методов
(`getUpdates`, `sendMessage`, `editMessageText`, `sendChatAction`, `getMe`,
`leaveChat`); библиотека-обёртка дала бы зависимость и свой цикл событий, а
`httpx` уже есть и подменяется в тестах `MockTransport`. Адрес API —
параметр (`TELEGRAM_API_BASE`, по умолчанию `https://api.telegram.org`): в
доказательном прогоне бот ходит в подменный Bot API на этой машине.

**D-T03. Long polling.** `getUpdates(offset, timeout=25, allowed_updates=["message"])`;
Updates сортируются по `update_id` и обрабатываются последовательно до
окончательной доставки ответа. Только затем следующий `offset` записывается
в `memory/service/telegram-offset`; Telegram подтверждает update при следующем
`getUpdates` с большим offset. Ошибки обработки или окончательной отправки
не позволяют продвинуть границу или обработать последующий update.
Неподдерживаемые/недопустимые updates завершаются без модели согласно правилам
доступа; для отказа чужому и выхода из группы терминальны только per-update
400/403, а временные ошибки требуют повтора.

Checkpoint содержит следующий номер; `telegram-offset.pending` — `v1`,
старую и новую границы. Пользовательские тексты не сохраняются. Запись:
уникальный временный файл → flush/fsync → атомарная замена → fsync каталога;
pending фиксируется перед основным файлом и удаляется после него с fsync
каталога. Незавершённый переход восстанавливается со старой границы;
повреждение или несогласованность — отказ, а не угадывание offset.
При аварии после доставки, но до фиксации возможна повторная отправка.
Exactly-once не гарантируется, и Telegram хранит updates ограниченное время.

Ошибка сети или 5xx Telegram — пауза 2 → 4 → … → 60 с и повтор;
429 учитывает `retry_after`; 409 Conflict
(второй опросчик) — понятное сообщение в лог и выход с кодом ≠ 0. Токен
проверяется `getMe` при старте.

**D-T04. Владелец — один Telegram ID.** `TELEGRAM_OWNER_ID` в `.env`;
проверяется `message.from.id` и тип чата `private`. Нет владельца в `.env` —
бот не отвечает никому и пишет в журнал «владелец не задан». Чужому —
«Это частный бот.» не чаще раза в сутки на ID (память процесса); в журнале
— «чужой» и первые 8 знаков sha256 от ID. Группа или канал — `leaveChat`.
ID владельца узнаётся консолью `--телеграм-кто` (только при остановленном
боте — иначе два опросчика): печатает ID, имя пользователя и время последних
сообщений боту, без текстов.

**D-T05. Ключ сервиса для бота.** `--телеграм-ключ` создаёт ключ «телеграм»
(права `чат`, `документы`) и сохраняет его в `memory/service/telegram.key`
(0600); старый ключ с тем же именем отзывается. Бот читает файл при старте.

**D-T06. История — в памяти процесса.** На чат — последние 12 реплик (6 пар).
Ответ сервиса 413 `context_length_exceeded` — бот убирает самую старую пару и
повторяет, пока не поместится; не помещается и один вопрос — сообщение
«вопрос длиннее окна модели (N токенов при пределе 3400)». После
перезапуска истории нет — бот говорит об этом в `/help`. На диск тексты не
пишутся (spec, § 10).

**D-T07. Поток в Telegram.** Сразу — сообщение-заготовка «⏳ …»; комментарий
SSE сервиса `: очередь N` → «⏳ в очереди сервиса: впереди N»; пока ждём —
`sendChatAction typing` раз в 4 с. Кусок текста → правка не чаще раза в
1,5 с и только если текст изменился (иначе Telegram отвечает 400 «message is
not modified»). Конец — правка с подписью «loc-rag-docs · вход N · ответ M
токенов · очередь Q с · всего T с». Итог (версия 5) — с разметкой: частый
Markdown модели («**жирно**», `код`, заголовки «###», списки «*   …») — в HTML
Telegram, остальное экранируется; Telegram не разобрал — тот же текст простым;
правки по ходу потока — простым текстом. Больше 4000 символов —
продолжение новым сообщением. 429 Telegram на правку — пауза по
`retry_after` и счётчик в журнале.

**D-T08. Одно дело за раз.** Production polling вызывает обработку до конца,
а не метод постановки в `asyncio.Queue`: следующий обычный update ждёт
завершения предыдущего. Мгновенные команды (версия 7, решение владельца):
пока update обрабатывается (`_с_боковым_опросом`), раз в
`ОПРОС_ВО_ВРЕМЯ_ОТВЕТА_С` = 2 с идёт `getUpdates(offset = номер текущего,
timeout = 0)` — Telegram отдаёт текущий и следующие, ничего сверх уже
подтверждённого не забывая; `/status`, `/help`, `/start` владельца из них
отвечаются сразу, их номера запоминаются в памяти. Основной цикл, дойдя до
такого update по порядку, только сдвигает checkpoint — он растёт по сплошному
префиксу завершённых. Ошибка бокового опроса не мешает основному; после аварии
мгновенная команда может прийти повторно. Совместимый метод `обработать`
сохраняет внутреннюю очередь для отдельных вызовов и тестов. Сервис по-прежнему
даёт одну генерацию, дополнительная очередь не вводится.

**D-T09. Отказы сервиса.** 429 — и `queue_full`, и `rate_limited` —
повторяемые, до общего срока 1200 с (как `service_load.py`). `queue_full`
(версия 3): правка «⏳ очередь сервиса занята — повторю, как только освободится
место (не позже чем через N с)», затем раз в 5 с `GET /health` — есть место
(«ждут» меньше мест очереди) — повтор сразу; `Retry-After` — только верхняя
граница: оценка «медиана × очередь» бывает и 1,5 с, и 741 с при очереди,
разобравшейся за 90 с. `rate_limited` — пауза по `Retry-After` (ведро ключа
считает точно). Оба кода
повторяемые: после коротких запросов `Retry-After` бывает ≈ 8 с, и повторы
раз в 8 с — это 7,5 запроса в минуту, больше лимита ключа 6/мин; `/status`
поэтому ходит в `/health`, а не в `/v1/*`. 413 `question_too_long` (`/doc`
длиннее 1000 знаков) — «вопрос длиннее 1000 знаков»; 401/403 — «ключ бота не принят / у ключа нет права
«документы»» (подсказка `--телеграм-ключ`); сеть до сервиса — «сервис не
отвечает: python cli.py --сервис статус»; 5xx и ошибка внутри потока —
«ошибка сервиса: код».

**D-T10. Документы и фильтр ПД — `agent/service/pd.py`.** Шаблоны Дня 29
переносятся сюда (`ШАБЛОНЫ`, `фамилии()`), а `optbench.без_пд` импортирует их
отсюда — поведение Дня 29 не меняется (его тесты). Новое: `скрыть(текст) ->
(текст, виды)` — каждое совпадение заменяется «[скрыто]»; поиск — по тексту, где
латинские двойники кириллицы заменены кириллицей (замена посимвольная, позиции
те же), инициалы — в любом написании, остатки инициалов у «[скрыто]» скрываются
(версия 4); фамилия из списка
— целым словом от основы (основы в `pd-names.txt` — начала фамилий).
`/doc` собирает ответ: текст; «Источники:» — файл и раздел; «Цитаты:» — текст
и отметка проверки («✓ дословно»), с «сокращена», если в цитате что-то
скрыто; затем «скрыто фильтром ПД: N (виды)». Маска — на всё, что уходит в
Telegram; перед отправкой — контрольная проверка `без_пд(итог) == []`, иначе
отправляется только «ответ скрыт: фильтр ПД не справился» (не должно
случаться; тест).

**D-T11. Сеть процесса бота.** В `offline.py` — разрешённые **внешние** хосты
(`OFFLINE_ALLOW_EXTERNAL`, через запятую): пропускаются, но считаются
внешними и видны по имени в журнале; всё прочее внешнее — блок. В путях
журнала сети `/bot<токен>/` заменяется на `/bot…/` для любого хоста. Логгеры
`httpx`/`httpcore` в процессе бота — уровень WARNING (на INFO `httpx` печатает
URL с токеном). Бот: `OFFLINE_ALLOW_EXTERNAL=api.telegram.org`; сервис —
127.0.0.1 (петля, локальный).

**D-T12. Журнал и состояние бота.** `memory/service/telegram.jsonl` (ротация
как у журнала сервиса): время, кто, вид, код сервиса, токены, ожидание,
длительность, правок, 429 Telegram, скрыто ПД (число и виды). Файл
состояния `memory/service/telegram-state.json` (раз в цикл опроса): pid, имя
бота, владелец задан, последний успешный опрос, счётчики, снимок журнала сети
процесса бота. `/admin/api/state` отдаёт `"telegram"` из этих двух файлов;
`/admin/api/telegram` (`POST {"действие": "старт"|"стоп"}`, ключ «админ»)
управляет службой — то же, что консоль. **ID владельца в состояние не
пишется** — только «задан / не задан»: странице и кадрам видео нечего
раскрыть.

**D-T13. Доказательный прогон — подменный Bot API + живой сервис.** Настоящий
Telegram нельзя проверить автоматически (сообщения пишет человек), поэтому
`check_telegram.py` поднимает на 127.0.0.1 подменный Bot API (тот же формат
JSON: `getUpdates` отдаёт подготовленные сообщения, остальные методы
записываются) и запускает **настоящий процесс бота** с `TELEGRAM_API_BASE`
на него — против **живого сервиса и модели**. Живая часть с настоящим
Telegram — по ключу `--живой`: `getMe` и одно сообщение владельцу «проверка
связи»; ответ модели в настоящем Telegram — ручная проверка с телефона и
видео.

**Проверка не трогает живого бота.** Бот проверки запускается со своей
памятью (`MEMORY_DIR` во временном каталоге, как `Стенд` в
`check_service.py`): свои `telegram-offset`, `telegram.jsonl`,
`telegram-state.json` — подменные `update_id` не сдвигают offset живого
бота, а карточка `/admin` не показывает данные проверки. Ключ сервиса —
свой, `проверка-телеграм` (создаётся живым, отзывается в `убрать()`), и
части 3 и 6 проверяют журнал сервиса именно по нему. Живой бот может
работать во время проверки: у него другой адрес Bot API, конфликта опроса
(409) нет.

**D-T14. Видео — Telegram Web в отдельном профиле.** `demo_telegram.sh`:
профиль Chrome `memory/telegram-web/` (0700). Первый запуск
(`--вход`) открывает `web.telegram.org/k/` для входа по QR — его делает
владелец; профиль сохраняется для дублей. Показ: окно шириной 880 — Telegram Web K
показывает одну колонку (ворота 0, A-T3: 680–880; при 600 и уже список
чатов частично виден), сразу `#@AIChBot`; вторая вкладка — `/admin`. Скрипт пишет только в поле ввода
этого чата и читает только сообщения этого чата. Запись — `record_demo.sh
--pid`, ускоренная копия — `demo_speedup.py`; кадры — `out/ocr30.sh` плюс
поиск токена и ID владельца по значению.

**D-T15. Консоль.** `--телеграм установить|старт|стоп|перезапуск|статус`
(статус: служба, имя бота по `getMe`, владелец задан, последний опрос,
счётчики), `--телеграм-ключ`, `--телеграм-кто`. Секреты в выводе не
печатаются.

## 5. Проверки до прогонов (тесты пишутся раньше кода модуля)

- `МаскаПД` — каждый вид шаблона скрыт; фамилия от основы целым словом;
  без `pd-names.txt` — общие шаблоны и предупреждение; `без_пд` Дня 29 — то
  же, что раньше.
- `СетьБота` — разрешённый внешний хост пропущен и посчитан внешним; другой
  внешний — блок; токен в пути скрыт; поведение без новой переменной — как в
  Днях 27–30.
- `БотTelegram` (`MockTransport` для Bot API и сервиса) — владелец и чужой,
  отказ раз в сутки, группа; поток: заготовка, правки не чаще порога, без
  одинаковых правок, подпись; история и `/new`; 413 → укорачивание; 429 →
  повтор; 401/403/сеть/5xx — тексты; очередь бота; длинный ответ — два
  сообщения; 429 Telegram на правку; `/doc` с маской и контрольной
  проверкой; `/status`; offset после перезапуска; журнал без текстов;
  логгер `httpx` не печатает токен.

## 9. Риски

| Риск | Что делаем |
|---|---|
| VPN выключен — Telegram недоступен | бот ждёт с нарастающей паузой; `/admin` показывает «последний опрос N мин назад»; в видео и проверке — заранее проверить VPN |
| Telegram ограничивает частоту правок | порог 1,5 с, правка только при изменении текста, пауза по `retry_after` (A-T2) |
| В кадре — личные чаты владельца | узкое окно с одной колонкой, вход прямо в чат бота, OCR всех кадров, просмотр глазами; при сомнении — дубль |
| Фильтр ПД пропустит фамилию не из списка | список `pd-names.txt` — основы подписантов (День 29); контрольная проверка перед отправкой; в документах предупреждение, что фильтр — по шаблонам |
| Токен утечёт в журнал или лог | маска в журнале сети, WARNING у `httpx`, поиск по значению перед коммитом и в кадрах |
| Изменение `offline.py` заденет Дни 27–29 | новая переменная по умолчанию пуста; тесты Дней 27–29 и полный `check_cli.py` |
| Бот — второй тип клиента, повторяющего по `Retry-After` | оба кода 429 повторяемые; нижняя граница `Retry-After ≥ 60/лимит` на сервере — довод за неё, но вне рамок, пока владелец не попросит |
| Фильтр ПД — по пяти видам | границы названы в `/help`, README и RESULTS; документы в Telegram — выбор владельца |
