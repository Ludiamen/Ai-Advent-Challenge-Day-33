# День 33 — ассистент поддержки пользователей: спецификация

Документ отвечает на вопросы «что» и «зачем». Как это строится — в [plan.md](plan.md), по
каким шагам — в [tasks.md](tasks.md). Код пишется после подписи владельца.

## 1. Задание (дословно)

> День 33. Ассистент поддержки пользователей
>
> Сделайте мини-сервис для поддержки пользователей.
> Ассистент должен:
> 👉 отвечать на вопросы о продукте
> 👉 использовать RAG (FAQ, документация)
> 👉 учитывать контекст пользователя или тикета
>
> Через MCP:
> 👉 подключите CRM
> 👉 или JSON с пользователями / тикетами
>
> Пример:
> 👉 «Почему не работает авторизация?»
> 👉 ассистент отвечает с учётом данных тикета
>
> Результат: AI-ассистент для поддержки пользователей
>
> Формат: Видео + Код

## 2. Что говорят лекция недели 7 и автор курса

Лекция: неделя продуктовая — собрать изученное в рабочий продукт; пайплайн с надёжностью
(повторы, запасной путь, детерминированные проверки), **человек в цепи** и **опасные
операции только с подтверждением**, метрики (время, стоимость, качество, доля без
вмешательства человека).

Автор курса в обсуждении задания (2026-10-14):
- «нужно развернуть условно **AI-first сервис на коленке — типа своей CRM**»;
- «раз мы делаем ИИ, то **чат** логичнее» (а не одиночный запрос-ответ);
- «доменная область, решение конкретной проблемы и создание **рабочего** чего-то имеет
  радикальное значение; MCP и RAG будут уметь многие, а сделать из этого рабочий продукт —
  отдельная задача»;
- VPS — «хотелось бы».

## 4. Что уже есть и чего не хватает

**Есть:** индекс документации CRM (1148 фрагментов, 58 файлов, ПД замаскированы), BM25
(`agent/rag/lexical.py`), ответ с цитатами и проверкой кодом (`agent/rag/cite.py`), «не
знаю» без опоры, клиент ds-flash и локальные модели, MCP-клиент и серверы Дней 16–20,
заявки на изменяющие вызовы с подтверждением человека (трекер Дня 17), шлюз Дня 30 (HTTPS,
ключи, лимиты, очередь, журнал без текстов), маска ПД, метрики Дней 31–32.

**Не хватает:** модели данных сервис-деска и её JSON, MCP-сервера `support`, FAQ, ассистента
поддержки (роль, контекст тикета, решение «ответить / уточнить / передать человеку /
предложить действие»), жизненного цикла тикета, чата пользователя и пульта, консоли,
контрольного набора, Docker-образа и развёртывания на VPS.

## 6. Требования

### 6.1 Функциональные

- **FR-01. Данные сервис-деска.** `support-seed.json` в репозитории (синтетика): пользователи
  (id, отображаемое имя без ФИО, роль, подразделение, почта `@example.invalid`, состояние
  учётной записи: активна / заблокирована (когда, почему, число попыток), второй фактор
  подключён / нет, резервных кодов осталось, пароль сменён (дата), последний вход, новое
  устройство), журнал входов (время, итог, причина отказа, устройство), тикеты по схеме
  `servicedesk.Ticket` (номер, тема, заявитель, статус и вид статуса, категория,
  критичность, сообщения с автором и временем, решение), справочники (статусы, категории).
  Рабочая копия — `memory/support/desk.json` (вне git); `--поддержка-сброс` восстанавливает
  её из seed. Не меньше 8 пользователей и 12 тикетов, покрывающих сценарии: блокировка,
  второй фактор не подключён, потерян телефон (резервные коды), пароль забыт / истёк,
  сессия истекла, вход с нового устройства, вопрос о заявке и её статусе, вопрос без ответа
  в документации.
- **FR-02. MCP-сервер `support`** (stdio, SDK `mcp` 2.x). Инструменты ассистента —
  **в границах одного тикета**: тикет (с сообщениями), заявитель тикета (профиль и
  состояние учётной записи), его журнал входов, его прошлые тикеты; запись: сообщение
  ассистента в тикет, смена статуса в пределах разрешённых переходов ИИ, **заявка на
  действие** (разблокировать, сбросить второй фактор, выслать ссылку на смену пароля,
  выдать новые резервные коды, передать человеку) — заявка ждёт подтверждения. Инструменты
  пульта (очередь, любой тикет, выполнить или отклонить заявку, закрыть с решением) —
  отдельный набор, **модели не выдаются**. Чужого пользователя ассистент не видит: сервер
  отвергает запросы вне тикета (тест, а не промпт).
- **FR-03. FAQ.** `support/faq.md` (в шапке: «по спецификациям портала; реализация идёт
  срезами»; в публичном репозитории — только с «да» владельца, иначе вне git, как индекс)
  — вопросы пользователей портала о входе, втором факторе,
  резервных кодах, паролях, сессиях, новом устройстве, заявках и уведомлениях; каждый ответ
  со ссылкой на спеку или решение CRM, откуда он взят. Проверка: каждая ссылка существует в
  индексе CRM, утверждения FAQ сверены со спеками (судья + просмотр).
- **FR-04. Поиск по документации.** Индекс поддержки: фрагменты документации CRM (из
  индекса Дней 31–32) и FAQ; поиск BM25; FAQ — в приоритете при равной близости. Индекс
  поставляется в образ и на VPS файлом (без модели эмбеддингов).
- **FR-05. Ассистент поддержки.** На сообщение пользователя в тикете:
  1. код через MCP берёт тикет, профиль и состояние учётной записи заявителя, журнал входов
     (последние N), прошлые тикеты;
  2. поиск по FAQ и документации (запрос — сообщение + тема + факты учётной записи);
  3. модель (роль «первая линия поддержки портала ИТ-отдела») отвечает JSON: ответ
     пользователю, источники и цитаты (проверяет код), **факты тикета**, на которые опирается
     ответ (проверяет код — они есть в данных MCP), решение: `ответ` | `уточнить` |
     `передать_человеку` | `предложить_действие(вид, причина)`;
  4. без опоры и без фактов — не выдумывать: «уточнить» или «передать человеку»;
  5. ответ пишется в тикет сообщением ассистента, статус — по решению (ждёт ответа
     заявителя / передан специалисту / ждёт подтверждения действия), заявка на действие —
     в MCP.
  Контекст тикета и сообщения пользователя — недоверенные данные (метки «данные тикета»,
  инструкции внутри не выполняются). Маска ПД на выходе.
- **FR-06. Чат пользователя** (`/support`). Пользователь входит по своей ссылке-ключу
  (синтетические пользователи; на VPS — ключи доступа), видит свои тикеты, пишет: новое
  сообщение без тикета создаёт тикет (тема — из первого сообщения), продолжение — в выбранном
  тикете; ответ ассистента — в чате с источниками («из FAQ: …», «по правилам входа: …») и
  статусом тикета; история разговора сохраняется; оценка ответа 👍/👎.
- **FR-07. Пульт поддержки** (`/support/desk`, ключ сотрудника). Очередь тикетов (по
  статусу и времени), тикет: переписка, профиль заявителя, журнал входов, ответы ИИ с
  источниками; **заявки на действия**: подтвердить (действие выполняется над данными
  сервис-деска, заявителю — сообщение) или отклонить с причиной; ответить вручную; закрыть
  с решением; вернуть ИИ.
- **FR-08. Консоль.** `cli.py --поддержка ...`: спросить как пользователь (`--пользователь
  ID`, `--тикет N`), очередь, тикет, заявки, подтвердить / отклонить, сбросить данные,
  метрики. Паритет с вебом.
- **FR-09. Мини-сервис** `support_app.py` (FastAPI): страницы чата и пульта, API
  `/api/support/...`; HTTPS и ключи — как в шлюзе Дня 30 (дома — свой центр сертификации;
  на VPS — Let's Encrypt при домене или свой центр); лимит запросов на ключ; журнал без
  текстов.
- **FR-10. Запасной путь.** Облако не ответило — повтор, затем (дома) локальная модель с
  пометкой, (на VPS) честное «передано специалисту, ИИ временно недоступен» — тикет не
  теряется. Сбой MCP — ответ без контекста тикета не даётся: «передано специалисту».
- **FR-11. Метрики.** На ответ — строка без текстов: время, токены, стоимость, решение,
  источники, факты, повтор, сбой; сводка: p50/p95, доля решённых ИИ без человека
  (deflection), доля передач человеку, доля подтверждённых / отклонённых заявок, оценки 👍/👎.
- **FR-12. Docker и VPS.** `Dockerfile` (python-slim, зависимости поддержки без
  llama-cpp, onnxruntime, Flask), `docker-compose.yml`, том данных; работает на 1 vCPU / 1 ГБ;
  инструкция развёртывания `DEPLOY.md`; проверка на VPS — тот же smoke-скрипт.

### 6.2 Нефункциональные

- **NFR-01. Данные.** В репозитории, образе и на VPS — только синтетические пользователи и
  тикеты (без ФИО, почта `@example.invalid`, телефоны не выдумываются); документация CRM —
  фрагменты индекса после маски ПД; публикация документации CRM на VPS — с подтверждения
  владельца при развёртывании.
- **NFR-02. Границы доступа.** Пользователь видит только свои тикеты; ассистент — только
  тикет и его заявителя; пульт — по ключу сотрудника; действия над учётными записями —
  только подтверждением сотрудника.
- **NFR-03. Время.** Ответ ассистента ds-flash — до 15 с (цель 8 с); на VPS — так же.
- **NFR-04. Память.** Мини-сервис в Docker — до 400 МБ RSS на VPS 1 ГБ.
- **NFR-05. Деньги.** ds-flash — центы на разговор; ds-pro — только судья набора.

## 9. Конституция дня

1. **CRM — только чтение**, её база и контейнеры не трогаются; документация — из индекса.
2. **Синтетика**: ни одного настоящего человека в данных; `pd-names.txt`, `.env`, `memory/`,
   `index*/`, `out/`, `demo/` — вне git; токены и ключи ищутся перед коммитом по значению.
3. **Действия над учётными записями — только подтверждением человека** на пульте.
4. **Службы `day31-*` и Ollama не трогаются**; порты 5000, 5001, 8443, 8444, 8766, 11435
   заняты — сервис поддержки дома на своём порту.
5. **VPS** — разворачивается с подтверждения владельца (доступ, публикация документации).
6. **Запись** — только окно браузера, кадры Chrome.
7. **Ничего не пушить**: `main` — владелец.
