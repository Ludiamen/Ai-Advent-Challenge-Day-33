# Устройство агента

Документ отвечает на три вопроса: из чего агент собран, кто кому что передаёт и
почему разделение проведено именно так. К модели памяти со временем добавились
слои управления: **предпочтения** (как отвечать этому человеку), **сценарии**
(что делать на такой запрос), **инварианты** (чего нельзя никогда), в Дне 15
**ворота перехода** (чем заслужен следующий этап задачи), в Дне 16 **слой
MCP** — внешние инструменты по Model Context Protocol, — в Дне 17 агент начал
этими инструментами **пользоваться**: свой сервер вокруг чужого API, вызовы по
решению модели и заявка на всё, что меняет данные. В Дне 18 добавилось
**время**: планировщик и фоновый работник, благодаря которым агент делает
работу, когда его никто не спрашивает. В Дне 19 появилась **композиция**:
цепочка инструментов, описанная заранее, где результат одного шага становится
аргументом следующего. В Дне 20 агент сам выбирает серверы и ведёт длинный
флоу. В Дне 21 появились **собственные знания**: индекс документов организации
(RAG) — рядом с памятью агента, но отдельно от неё. В Дне 22 агент начал этим
индексом **отвечать**: RAG-запрос с фрагментами в промпте и тот же вопрос без
них, сравнение на контрольных вопросах. В Дне 23 у поиска появился **второй
этап**: реранкер переоценивает кандидатов, порог отсекает лишнее, в промпт идёт
top-K; вопрос можно переписать в несколько запросов на языке документов. В Дне
24 ответ обязан **опираться на документ**: источники и дословные цитаты,
проверенные кодом, и «не знаю» с уточнением, когда опереться не на что. В Дне
25 всё это стало **разговором**: мини-чат хранит историю, ищет по базе на
каждой реплике и держит **память задачи** — цель, уточнения, ограничения и
термины пользователя, — чтобы длинный диалог не терял, зачем он начат. В Дне
26 модель переехала **на этот компьютер**: Ollama с моделями 1.7B–4B стала ещё
одним провайдером каталога — без ключа, без оплаты, запрос не покидает машину.
В Дне 27 приложение научилось работать **офлайн**: роли агента переходят на
локальные модели по карте ролей, а сеть закрыта для всего, кроме этой машины.
В Дне 28 локальная модель встала в **RAG-конвейер**: поиск без LLM, ответ с
цитатами на CPU и сравнение с облаком по качеству, скорости и стабильности. В
Дне 29 эта модель **оптимизирована под задачу** — параметры вызова, кванты,
шаблон промпта и параметры сервера замерены по отдельности, а итог стал своей
моделью Ollama `loc-rag-docs` на роли ответа по документам. В Дне 30 она стала
**приватным сервисом**: шлюз перед Ollama со службой systemd, HTTPS, ключами,
лимитами и очередью отвечает по сети — по OpenAI-совместимому API, в чате и
по документам. В Дне 31 агент получил **ассистента разработчика**: `/help вопрос`
о настоящем проекте (CRM владельца, только чтение) — по индексу его документации,
схем данных и маршрутов API и по git через свой MCP-сервер только на чтение; в
консоли, на странице чата и в Telegram через ручку сервиса.

## Слой MCP (День 16)

```
  mcp-servers.json ──load()──> [Server]  транспорт, адрес, env/headers с подставленными
        │                                ${ПЕРЕМЕННЫМИ}, фильтр разрешить/запретить
        v
  Registry.inspect()  ── ThreadPoolExecutor, поток на сервер ──┐
        │                                                       v
        │                                  Session(server)      поток + цикл событий anyio
        │                                    open()             задача-владелец держит
        │                                      stdio_client ─┐  контекст SDK до close()
        │                                      streamable ───┤
        │                                    mcp.Client ─────┘  server/discover | initialize
        │                                    tools()            tools/list по nextCursor
        v
  [Inspection]  рукопожатие, [Tool], ошибка + этап + подсказка + stderr сервера
        │
        +──> cli.py --mcp           печать списка
        +──> web.py /api/mcp*       панель «MCP-серверы»
        +──> check_mcp.py           сверка с сырым JSON-RPC, JSON Schema, имена
```

**Слой не зависит от агента.** `agent/mcp/` не импортирует ни память, ни
модели. Консоль обрабатывает `--mcp` до создания `MemoryAgent`, а веб-ручки
его не трогают. Список инструментов — свойство серверов, а не разговора. Связь
с агентом появилась там, где она понадобилась, — в Дне 17, и односторонняя:
агент берёт у `Toolbox` описания разрешённых инструментов и по имени
`сервер__инструмент` находит, к какому соединению идти с вызовом.

**Почему соединение — объект с потоком, а не `asyncio.run()` на операцию.** SDK
асинхронный, агент синхронный. Разовый `asyncio.run()` годится для «получить
список и выйти», но в диалоге модель вызывает инструменты много раз, и каждый
раз заново запускать сервер (`npx` — это 3 секунды) нельзя. Поэтому `Session`
держит цикл событий в своём потоке (`BlockingPortal`), а контекст клиента SDK
открыт в одной задаче-владельце. Anyio требует закрывать контекст с группой
задач в той же задаче, где его открыли. Операции идут через портал с
`fail_after`, а таймаут открытия отсчитывается снаружи по событию «готово».
Таймаут внутри задачи пришлось бы ставить на вход в контекст, который потом
остаётся открытым, и anyio этого не допускает.

**Три уровня защиты.** Фильтр в файле решает, какие инструменты вообще видны
модели. Пометки сервера (`readOnlyHint` и прочие) только объясняют, что
закрывать: спецификация велит не доверять им у непроверенного сервера. Код
своего сервера сам проверяет аргументы, потому что имя пользователя приходит
от модели.

**Свой сервер** (`mcp_server.py`) читает хранилища агента напрямую —
`WorkingMemory`, `InvariantStore`, `ProfileStore`, `ConditionStore`,
`DecisionsStore`, — а не через `MemoryAgent`. Агент при создании открывает
SQLite, раскладывает начальное наполнение и готовит клиентов моделей. Серверу
только для чтения ничего из этого не нужно, а создавать файлы он не должен.

## Свой инструмент и вызовы (День 17)

```
  tracker_api.py         чужой API: HTTP, OAuth-токен, коды 401/403/404/422/429
   (мок; тот же код    ▲   /v3/issues/_search · /v3/issues/{key} · comments · transitions
    работает и с       │
    api.tracker.       │ httpx
    yandex.net)        │
                    tracker_server.py     MCP-сервер ВОКРУГ API
                       @сервер.tool         регистрация + пометки поведения
                       Annotated + Field    описание входных параметров -> JSON Schema
                       выжимка (_карточка)  возврат результата: только нужное модели
                       ToolError            ошибка API -> причина, понятная модели
                       ▲ stdio | HTTP
                       │
  agent/mcp/toolbox.py  Toolbox: открытые сеансы, плоский список «сервер__инструмент»,
        │               .для_модели() -> tools запроса, .вызвать(имя, аргументы)
        v
  MemoryAgent.ask ──> llm.Client.call(..., tools=[...])
        │                    ответ: tool_calls        <- модель ПРОСИТ вызов
        │             _исполнить_просьбу(просьба)
        │                 читающий  -> Toolbox.вызвать -> role=tool с результатом
        │                 меняющий  -> MemoryManager.request_call -> ЗАЯВКА, вызова нет
        │             до MAX_TOOL_ROUNDS кругов, потом запрос без инструментов
        v
  Answer.вызовы / Answer.заявки ──> cli.py (строки «↳», --заявки, --подтвердить)
                                └─> web.py (/api/tools, /api/mcp/call, /api/calls)
        │
  confirm_call(N) ──> Toolbox.вызвать ──> изменение в чужой системе + запись в память
```

**Почему сервер вокруг API, а не вокруг файла.** Вчерашний `mcp_server.py`
читает файлы памяти; там нет ни авторизации, ни кодов ответа, ни лимитов. API
даёт всё это сразу: токен в заголовке, 401 при негодном токене, 403 при чужой
организации, 404 на несуществующую задачу, 422 на недопустимый переход, 429 при
частых запросах. Работа обёртки как раз в том, чтобы каждое из этих состояний
дошло до модели словами, а не исключением.

**Мок и настоящий Трекер — один код.** `tracker_server.py` не знает, с кем
говорит: адрес, токен и организация приходят из окружения, а его задаёт
`mcp-servers.json` — сервер `tracker` смотрит в мок, `tracker-real` в
`api.tracker.yandex.net`. Это и проверка честности обёртки: если бы она знала
про мок, «сервер вокруг API» был бы словами.

**Чтение и запись разведены на уровне списка инструментов.** Меняющие
инструменты регистрируются только при `TRACKER_WRITE=1`. У настоящего Трекера
по умолчанию их нет вовсе: чего нет в `tools/list`, того модель не попросит.
Это дешевле любой проверки внутри вызова и видно снаружи обычным списком.

**Три рубежа перед изменением чужих данных.** Первый — список: меняющего
инструмента может не быть. Второй — `Toolbox.меняет()`: читающим считается
только то, что сервер сам пометил `readOnlyHint`; всё остальное, включая
инструменты без пометок, считается меняющим. Третий — заявка: агент не
выполняет вызов, а записывает его в `memory/tool-calls.json` и ждёт человека.
Заявка живёт в файле, а не в памяти процесса, потому что ответ пришёл в одном
процессе (веб-запрос), а подтверждение придёт в другом — как пауза задачи в
Дне 13.

**Результат инструмента — данные, не указания.** Ответ приходит из чужой
системы: комментарий в трекере может написать кто угодно, в том числе «игнорируй
прежние указания». Для модели это такой же текст в контексте, поэтому граница
объявлена в системном промпте (`prompts.ИНСТРУМЕНТЫ`), длина ответа ограничена
(`ПРЕДЕЛ_ОТВЕТА`), а по-настоящему защищает то, что изменение всё равно требует
подтверждения человеком.

**Круги вызовов ограничены.** Модель, которой инструмент отвечает ошибкой,
склонна звать его снова и снова, а каждый круг — это полный запрос вместе со
всей перепиской. После `MAX_TOOL_ROUNDS` агент делает последний запрос без
инструментов: «ответь по тому, что уже получено».

## Планировщик и фоновая работа (День 18)

```
  человек / модель                            работник — ОТДЕЛЬНЫЙ ПРОЦЕСС
   cli.py --запланировать                      worker.py (systemd, nohup, терминал)
   web.py /api/scheduler/job                        │
   модель: schedule_job(...)                        │ каждые «тик» секунд
        │                                           v
        v                                     ScheduleStore.к_сроку(сейчас)
  scheduler_server.py  ─────────┐                   │
   6 инструментов:              │              опоздал > окна? ─да─> отметка «пропуск»
   list_jobs · schedule_job     │                   │нет           (не догоняем)
   cancel_job · remind          │                   v
   build_digest · latest_digest │             Toolbox.вызвать(инструмент, аргументы)
        │                       │                   │       └─> tracker_server, любой другой
        v                       v                   v
  memory/scheduler.db  <── SQLite (WAL) ──>  записать_запуск(результат)
   задания · запуски · сводки ·                     │
   напоминания · пульс работника                    ├─ перенести срок от «сейчас»
        │                                           └─ если это была сводка:
        │                                                 модель пишет по цифрам абзац
        v
  MemoryAgent.ask ──> Answer.сводка / Answer.напоминания (показываются ОДИН раз)
        └─> cli.py --задания/--сводка/--запуски, панель «Планировщик» на странице
```

**Почему отдельный процесс, а не поток в сервере.** stdio-сервер MCP живёт ровно
столько, сколько открыт сеанс агента: закрыли консоль — и «работа 24/7»
кончилась вместе с ней. Работник переживает и консоль, и страницу; его можно
положить в systemd. Связь с остальным агентом — через файл базы, как пауза
задачи в Дне 13, которую продолжает другой процесс.

**Почему работник — клиент MCP, хотя база у него под рукой.** Задание — это
вызов инструмента, а не «вид работы из списка». Работник не знает, что такое
трекер: он знает, что надо позвать `tracker__list_issues` с такими-то
аргументами и сохранить ответ. Поэтому в расписание можно поставить любой
инструмент любого сервера — в том числе того, которого ещё не написали. Цена
решения: работник поднимает MCP-сеансы, и соединения он держит открытыми между
обходами, добавляя сервер к уже открытым, а не пересобирая ящик.

**Почему SQLite, а не JSON, как у заявок Дня 17.** В один файл пишут сразу
несколько процессов: работник выполняет задания, MCP-сервер заводит и отменяет
их, консоль и страница читают. JSON пришлось бы переписывать целиком, и два
одновременных сохранения затёрли бы друг друга — теряя именно те записи, ради
которых всё затевалось. SQLite в режиме WAL разводит читателей и писателя сам.

**Расписание словами, а не cron.** Его пишут двое: человек в консоли и модель в
аргументах вызова. «каждые 30м» читается без справочника и не путается, в
отличие от `*/30 * * * *`, где ошибка выясняется через сутки. Разбор — десяток
строк и полностью покрыт тестами; цена честная: «по будням в 9 и 18» не
выразить.

**Пропущенное не догоняется.** Если срок прошёл давнее окна опоздания (минута
по умолчанию), задание не выполняется: в историю ложится отметка с числом
пропущенных сроков, а следующий срок считается от «сейчас». Иначе утро после
ночного простоя начиналось бы залпом из сорока вызовов и сорока сводок об одном
и том же моменте. Опоздание внутри окна — не пропуск: работник жив, просто занят.

**Сводка: цифры кодом, текст моделью.** Счётчики, различия между краями окна и
напоминания считает `agent/scheduler/digest.py` без единого вызова модели —
фоновой работе нельзя зависеть от того, ответил ли провайдер в три часа ночи.
Связный абзац по готовым цифрам пишет работник: MCP-серверу незачем знать про
ключи провайдеров и роли моделей. Различия ищутся по структуре JSON, без знания
о трекере, поэтому завтрашний сервер сравнится так же.

**Четвёртый рубеж: отложенное изменение.** Планировщик мог бы обойти
подтверждение из Дня 17 — «запланируй закрыть все задачи через минуту» меняет
чужие данные не сейчас, а когда до них дойдёт работник. Поэтому
`Toolbox.меняет(имя, аргументы)` спрашивает и о том, что вызов ставит в
расписание: планирование меняющего инструмента становится заявкой так же, как
прямой вызов. Правило описано полем `«планирует»` в `mcp-servers.json`.

**Граница «своё хозяйство / чужая система».** Записи планировщика — расписание,
напоминания, сводки — это собственная память агента, и ведёт он её сам, как
задачи и знания. Поле `«своё»` у сервера отличает её от чужой системы, иначе
каждое напоминание требовало бы заявки, а подтверждение перестало бы что-то
значить.

**Свежее показывается один раз.** Сводка и новые напоминания прикладываются к
ближайшему ответу агента и тут же помечаются прочитанными. Иначе одно и то же
висело бы под каждым ответом, человек перестал бы это читать — и не заметил бы
новое. Служебные шаги сценариев фоновое не получают: их текст собирается для
следующего шага.

## Композиция инструментов (День 19)

```
  pipelines.json ──Каталог.конвейер()──> Конвейер           проверка связей ДО вызовов:
        │                                 [Шаг: имя, инструмент, аргументы]   имена уникальны,
        │                                                   ссылка только назад, ${вход.…}
        v                                                   объявлен
  Исполнитель(ящик, хранилище).выполнить(конвейер, вход)
        │
        │   портфель = {"вход": {...}}
        │   для каждого шага:
        │       подставить(аргументы, портфель) ──> (готовые аргументы, след подстановок)
        │       ящик.вызвать(инструмент, аргументы) ──> ToolResult
        │       портфель[имя] = {"данные": …, "текст": …}
        │       записать_шаг(вход, подстановки, выход)      ← доказательство передачи
        │       сбой ──> прогон «сбой», цепочка обрывается
        v
  memory/scheduler.db: прогоны + шаги_конвейера
        │
        +──> pipeline_server.py   run_pipeline / last_run — протокол для модели
        +──> cli.py --конвейер    печать протокола со строками «получил …»
        +──> web.py /api/pipeline* панель «Конвейеры»
        +──> worker.py            конвейер как обычное задание расписания
        +──> check_pipeline.py    сверка вход/выход шагов прямым запросом к SQLite
```

**Где что лежит.** `agent/pipeline/` — четыре модуля: `values.py` (подстановка
`${шаг.данные.поле}`: как данные переходят дальше), `spec.py` (описание цепочки
и проверка её связей), `store.py` (прогоны и шаги в SQLite), `runner.py`
(исполнитель). Пакет не зависит ни от планировщика, ни от MCP: исполнителю
достаточно «ящика» — чего угодно с методом `.вызвать(имя, аргументы)`. Поэтому
одна и та же цепочка исполняется из консоли, со страницы, из работника по
расписанию и по просьбе модели.

**Почему сервер конвейеров — сам клиент MCP.** Шаг может звать инструмент
другого сервера (`tracker__list_issues`), и тогда `pipeline_server.py` открывает
к нему соединение как обычный клиент. Свои три инструмента он зовёт напрямую:
соединение с самим собой означало бы второй процесс сервера и вторую базу.
Композиция получается на уровне серверов, а не внутри одного модуля.

**Почему база общая с планировщиком.** Файл `memory/scheduler.db` один, таблицы
разные («прогоны», «шаги_конвейера» против «задания», «запуски»), классы тоже
разные и друг о друге не знают. Причина в том, что фоновая жизнь агента одна:
работник запускает конвейер по расписанию, сводка считает его прогоны, консоль
и страница читают и то и другое. Два файла означали бы две блокировки и вечный
вопрос, какой из них свежее.

**Подтверждение — на цепочку целиком.** `Toolbox.меняет()` для вызова
`run_pipeline` смотрит не на пометку самого инструмента, а на шаги названной
цепочки (поле `«конвейеры»` в `mcp-servers.json` говорит, в каком аргументе
лежит её имя). Это продолжение решения Дня 18 про отложенные вызовы: изменение,
спрятанное внутрь цепочки, — такое же изменение, просто дальше от глаз.

## Оркестровка серверов (День 20)

```
  запрос человека
        │
        v
  Маршрутизатор(серверы из mcp-servers.json)        ← описания, а не схемы
        │   круг дешёвой модели: «какие серверы нужны?»
        │   сбой/молчание ──> правила по «темам» (основы слов, не целые слова)
        │   фильтры: «по_просьбе» (боевой Трекер сам не берётся),
        │            «замещает» (два одинаковых сервера разом не открываются),
        │            не готов (нет ключа) ──> отсеян с причиной
        v
  Toolbox(выбранные серверы)      ← склад: на каждый набор свой, закрываются разом
        │
        v
  Оркестр.запустить(вопрос, промпт)
        │
        │  1. план: круг модели БЕЗ инструментов ──> План(шаги: инструмент + зачем)
        │     проверка плана правилами порядка ──> замечания (не запрет)
        │  2. круги с инструментами, на каждую просьбу — три заслона:
        │        есть ли инструмент ──> нет: список доступных уходит модели
        │        Порядок.проверить(имя, сделано) ──> нет: шаг «отклонён», вызова НЕТ
        │        Toolbox.меняет() ──> да: заявка + ПАУЗА флоу (не отказ)
        │  3. бюджет: кругов модели и вызовов инструментов
        │  4. сверка(план, шаги) ──> по плану / пропущено / сверх плана / порядок
        v
  memory/scheduler.db: флоу + шаги_флоу
        │
        +──> cli.py --флоу / --флоу-показать / --флоу-продолжить / --маршрут
        +──> web.py /api/flow*      панель «Оркестр»
        +──> digest.py              сводка считает флоу и те, что ждут человека
        +──> check_orchestra.py     порядок и пауза проверяются прямым SQL
```

**Зачем маршрут.** Серверов девять, инструментов полсотни (≈ 11 000 токенов
описаний), и они уходят в **каждый** запрос разговора. Это та самая квадратичная цена из лекции.
Маршрут стоит одного круга дешёвой модели на запрос, а снимает описания всех
неподошедших серверов со всех последующих кругов. Побочный выигрыш важнее
денег: из четырёх инструментов модель выбирает точнее, чем из шестидесяти.

**Почему выбор серверов — отдельный круг, а не часть основного.** Модель,
которой дали шестьдесят инструментов и попросили «сначала реши, какие из них
нужны», уже заплатила за все шестьдесят. Сэкономить можно только до того, как
схемы уйдут в запрос, — поэтому круг выбора видит девять строк описаний и
ничего больше.

**Почему план отдельно от исполнения.** Без плана «корректность выбора и
порядка вызовов» проверить нечем: журнал задним числом оправдывает любой
порядок. План — это намерение, записанное ДО первого обращения к чужой системе;
сверка в конце показывает, где факт от него отошёл. При этом план не закон:
модель узнаёт в работе то, чего не знала, когда планировала, и шаг сверх плана
— нормальная часть работы, он просто помечается.

**Почему порядок проверяет код, а не промпт.** Правило «комментарий — после
чтения задачи» в системном сообщении модель соблюдает не всегда, а цена
нарушения — комментарий, сочинённый по памяти диалога, в чужой системе.
`flow-rules.json` останавливает такой вызов до того, как он случится, и
объясняет модели, чего не хватает; в протоколе остаётся шаг «отклонён» — видно
и попытку, и то, что её остановил код.

**Почему меняющий шаг ставит флоу на паузу, а не отменяет его.** Ко второму
десятку вызовов у флоу накоплено многое: прочитанная задача, найденная память,
ответ документации, отчёт. Отказ на последнем шаге означал бы, что после «да»
человека всю эту работу придётся делать заново и оплачивать второй раз. Поэтому
флоу замирает вместе со своей перепиской в базе, а `--флоу-продолжить N`
поднимает её и дописывает результат подтверждённого вызова — тот самый, который
уже выполнил `confirm_call`, а не новый.

**Почему флоу не ставится в расписание.** Задание Дня 18 — это работа без
человека, а длинный флоу устроен так, что может человека потребовать: перед
изменением чужой системы он останавливается и ждёт «да». Ставить в расписание
работу, которая в середине замирает, значило бы обещать больше, чем она делает.
Связь с фоновой жизнью агента при этом есть, и она односторонняя: сводка Дня 18
считает флоу и отдельно называет те, что ждут подтверждения, — чтобы работа,
замершая на человеке, не потерялась между днями.

**Доверие к чужому серверу.** Публичный сервер документации не объявляет
`readOnlyHint` вовсе, и по правилу Дня 17 каждый вопрос к нему был бы
«изменением». Поле `«только_чтение»` в `mcp-servers.json` — это доверие,
которое даёт человек, составляющий файл, а не сервер, рассказывающий о себе.

## AI-ревью PR (День 32)

Пайплайн из лекции недели 7: триггер (PR) → вход (diff и изменённые файлы) → агент с LLM,
RAG и инструментами → результат (комментарий и статус) → человек решает. Подробно —
[REVIEW.md](REVIEW.md), требования — [specs/032-code-review/](specs/032-code-review/).

```
 GitHub: pull_request opened / synchronize / reopened / ready_for_review
   └─ .github/workflows/ai-review.yml (ubuntu-latest; contents: read, pull-requests: write;
      черновики пропускаются; concurrency на PR) → requirements-review.txt → review.py --github
 консоль: cli.py --ревью A...B, review.py --pr N      чат: /review [A...B] (консоль и /chat)
                     │
                     ▼
   agent/review/pipeline.py  выполнить(от, до, модель, канал, …) → ИтогРевью
     1. source.py    git-сервер MCP: git_changes (merge-base, статус, +/−, бинарный) →
                     git_diff по файлам (literal path, предел) → git_show головы;
                     фильтр (бинарные, lock, медиа) и пределы (25 файлов, 80 000 симв.)
     2. индекс       project.построить(advent, ссылка=merge-base): файлы из КОММИТА
                     базы (ls-tree + cat-file --batch), маска ПД, фрагменты индексатора
     3. context.py   запросы из diff (путь, изменённые def/class, идентификаторы;
                     импорты и адреса нового кода; заголовок PR; «конституция» и
                     «устройство») → BM25 (agent/rag/lexical.py) → пул фрагментов;
                     места вызова изменённых функций — git_grep + git_show базы;
                     функции головы вокруг изменённых строк — ast; второй этап —
                     BM25 пула по всему тексту изменений; свой отбор каждому ревьюеру
     4. reviewers.py баги │ архитектура │ рекомендации — ThreadPoolExecutor(3), свой
                     llm.Client у каждого, git_show (база и голова PR) ≤ 2 кругов;
                     JSON находок, один повтор формата, таймаут 150 с
     5. collect.py   код проверяет: файл из PR, строка в участке ±3, цитата diff
                     найдена (cite.найти), источники выданы; неподтверждённая
                     «критично» → «важно»; дубли сливаются; вердикт — красный ⇔
                     подтверждённая «критично» в багах или архитектуре
     6. render.py    markdown с меткой <!-- ai-review:advent -->, маска ПД,
                     экранирование HTML и @, скрытая строка метрик; консольный вид
     7. metrics.py   строка без текстов; базовая линия — медиана 20; тревога ×2
                     │
        ┌────────────┼──────────────────────────────┐
        ▼            ▼                              ▼
   github.py     $GITHUB_STEP_SUMMARY,         notify.py: sendMessage владельцу
   комментарий   артефакт review-metrics,      (красный, не выполнено, тревога) —
   по метке      код выхода 0 / 1 / 2 →        без кода и находок, маска ПД
   (обновить),   цвет проверки PR
   история и 👍/👎
```

**Почему так.**
- **Индекс из базы, а не головы.** Правила (ARCHITECTURE, конституции спек) берутся из того
  состояния, куда PR вливается: PR, который заодно правит документ, не может переписать
  правила, по которым его проверяют. Изменённые документы остаются в опоре версией базы;
  исключаются только фрагменты изменённого кода — их новая версия в diff и в контексте
  функций.
- **BM25, а не bge-m3, на раннере.** Раннер каждый раз пустой: bge-m3 на 4 ядрах — ≈ 5 с на
  фрагмент, весь репозиторий — часы. Лексический индекс собирается за секунды, а в коде
  идентификаторы значат больше смысловой близости. Слабое место — правила, сформулированные
  другими словами («вызов httpx» → «только через llm.Client»): его закрывают запросы по
  зависимостям нового кода и второй этап отбора; замер — spec A-1.
- **Модель предлагает — код решает.** Вердикт не спрашивается у модели: красный ставит
  сборщик по подтверждённым находкам. Выдуманная цитата или чужой файл не красят PR.
- **Инструменты ревьюера — только чтение.** `git_show` по двум коммитам PR; слияния, push,
  правок нет по построению. diff — данные в метках, подделка меток обезврежена.
- **Один конвейер на все входы.** Action, консоль и чат отличаются только тем, откуда база и
  голова и куда итог; `review.py` не импортирует `cli.py` и тяжёлые пакеты сервиса.

**Почему ассистент — отдельный модуль, а не ещё одна роль мини-чата.** Мини-чат Дня 25 не
вызывает инструменты и пишет память задачи; ассистенту нужен короткий цикл инструментов git
и своя роль, а память задачи владельца трогать незачем: `/help` — вопрос о проекте, а не
реплика разговора. Поэтому разбор `/help` стоит в каналах до хода чата, а ответ кладётся в
историю чата обычными репликами и в ленту `/help` сессии — без памяти задачи.

**Почему индекс — копия файлов под маской, а не новый индексатор.** Индексатор Дней 21–30
уже умеет `.md` по заголовкам и `.py` по `def`/`class`, кэширует векторы по тексту и пишет
`source` фрагмента — относительный путь. Файлы проекта после маски ПД точного профиля
кладутся в `index-projects/crm/src/` с теми же путями: маска гарантированно стоит до
разбиения, источник — путь в CRM, повторная сборка — из кэша (1136 фрагментов, секунды).
Только файлы под git (`git ls-files`): неотслеживаемое и игнорируемое в индекс не попадёт.

**Почему точный профиль маски.** Полный профиль Дня 30 сделан под распознанные договоры:
латинские двойники кириллицы и инициалы в любом написании. На технической документации он
превращал `ORM` в «OR[скрыто]», `MVP`, `IP`, `BODY.PEEK` — тоже. Точный профиль: фамилии из
`pd-names.txt` целым словом, e-mail, телефоны отдельным числом, инициалы с фамилией только
кириллицей. Полный профиль остался для `/doc`.

**Почему git — свой сервер, и как он «только читает».** Меняющих инструментов нет вовсе —
это ответ на «опасные операции» лекции конструкцией, а не проверкой. Но и чтение в чужом
репозитории опасно: `git status` берёт блокировку индекса (параллельная сессия CRM получила
бы `index.lock`), а локальный `.git/config` может назначить `core.fsmonitor`, внешний diff
или textconv — программы, которые git исполнит при чтении. Сервер выключает всё это на
каждом вызове; тест ставит такие ловушки во временном репозитории и проверяет, что они не
сработали (без защиты — срабатывают трижды).

**Почему в сервисе — DeepSeek и MCP.** Владелец выбрал путь бота через ручку сервиса и
облачную модель для неё. Процесс сервиса остаётся офлайн: внешний хост разрешён один —
`api.deepseek.com` (`OFFLINE_ALLOW_EXTERNAL`, с запуска — переключатель без перезапуска), и
облачную модель зовёт только ассистент ручки проекта; чат и документы — `loc-rag-docs`. В
режиме «локально» новых внешних запросов 0 — это проверяет `check_devassist.py`. MCP-сервер
git запускается дочерним процессом из `asyncio.to_thread` (допущение A-7, проверено под
systemd).

**Почему запись показа — кадрами Chrome.** Захват области экрана (x11grab) снимает всё, что
окажется поверх окна: в первую секунду показа окно Chrome ещё не поднялось, и в кадр попал
редактор владельца. `Page.startScreencast` отдаёт кадры самой страницы — чужое окно попасть
не может; в Telegram запись начинается после скрытия списка чатов.

**Шлюз, а не Ollama наружу.** Ollama слушает только 127.0.0.1 и не меняется
(служба не трогается). В сеть выходит отдельный процесс, у которого есть то,
чего у Ollama нет: ключи с правами, подсети, лимиты, очередь, журнал и HTTPS.
Интерфейс агента (`web.py`) с инструментами MCP наружу не выставляется: шлюз
знает только модель и ответ по документам.

**OpenAI-совместимый снаружи, `/api/chat` внутри.** OpenAI-ручка самой Ollama
не принимает `keep_alive`, `think` и `options`: модель выгружалась бы через 5
минут простоя, а ответ уходил бы в «размышления». Шлюз шлёт в `/api/chat` то
же, что агент (`think: false`, `keep_alive`, окно 4096, предел ≤ 600), и сам
собирает ответ в формат OpenAI: `usage` — из `prompt_eval_count`/`eval_count`,
`finish_reason` — из `done_reason`. Поэтому подключается любой клиент — проверено
официальным SDK `openai` из контейнера.

**Предел контекста — до модели.** В Ollama 0.34.4 нет подсчёта токенов. Шлюз
берёт словарь из GGUF-файла самой модели (`llama-cpp-python`, `vocab_only` —
веса не грузятся) и шаблон чата, измеренный против `prompt_eval_count`. Длинный
вход получает 413 за доли секунды, и очередь не занимается.

**Очередь — одна генерация.** На двух ядрах параллельные генерации замедляют
всех (День 29). Ждущих — не больше N; следующему — сразу 429 с `Retry-After`
(медиана последних 20 генераций × очередь). Это подсказка, а не обещание:
после коротких запросов медиана мала (1,5 с при генерации ≈ 70 с), после
длинных — велика (741 с при очереди, разобравшейся за 90 с). Поэтому клиент
нагрузки повторяет до общего срока запроса, а не по числу попыток, а
Telegram-бот ждёт место по `/health`. Клиент без потока видит своё место в
заголовках, в потоке — комментарий SSE `: очередь N`. Закрыл клиент соединение — шлюз
закрывает поток к Ollama, и Ollama прерывает генерацию; место освобождается.

**Лимит ключа — ведро.** Шесть запросов в минуту на ключ ко всем `/v1/*`;
у клиентов нагрузки свои ключи — так меряется очередь, а не лимит.

**Приватность — по слоям.** Подсети проверяются до ключа: ноутбук, унесённый в
другую сеть, чужим не отвечает. Ключи на диске — только хэши; ключи нагрузки и
сертификаты — в `$MEMORY_DIR/service/` (вне репозитория). Журнал запросов —
метаданные без текстов. Процесс сервиса — в офлайн-режиме Дня 27: облако и
внешние адреса заблокированы, журнал сети считает каждый запрос.

**Production polling — последовательный.** `опросить_раз` сортирует updates
по `update_id`, ждёт завершения обработки и окончательной доставки ответа,
затем сохраняет следующий offset. Следующий `getUpdates` подтверждает
завершённые updates; ошибка обработки или отправки не позволяет перейти к
следующему update. `/status`, `/start`, `/help` владельца — сразу: пока update
обрабатывается, раз в 2 с идёт короткий `getUpdates` с offset этого update
(Telegram хранит неподтверждённые), мгновенные команды из него отвечаются, а
checkpoint дойдёт до них по порядку и только подтвердит (решение владельца,
spec и plan — версия 7).
Совместимый метод `обработать` сохраняет внутреннюю очередь для отдельных
вызовов, но production polling не считает постановку в неё завершением.

**Checkpoint — метаданные.** `telegram-offset` хранит следующий номер,
`telegram-offset.pending` — `v1`, старый и новый номера. Текстов в них нет.
Временный файл синхронизируется, заменяется атомарно, затем синхронизируется
каталог. При pending-переходе восстановление использует старую границу;
несогласованные или повреждённые файлы вызывают отказ. Между доставкой ответа
и фиксацией checkpoint возможна авария и повторная отправка после рестарта.
Exactly-once доставка не гарантируется; история остаётся только в RAM.

**Бот — клиент, а не часть сервиса.** Боту нужен интернет (Telegram), сервису
— нельзя, поэтому это отдельный процесс и отдельная служба. Для сервиса бот —
ещё один ключ: лимиты, очередь, предел контекста и журнал без текстов к нему
применяются сами, а процесс сервиса остаётся с «внешних 0». Входящих
соединений нет: бот сам опрашивает Telegram, webhook не нужен.

**Bot API — своим клиентом на `httpx`.** Шесть методов, без библиотеки-обёртки:
и Telegram, и сервис подменяются в тестах `MockTransport`, а доказательный
`check_telegram.py` запускает настоящий процесс бота против подменного Bot API
на 127.0.0.1. Токен стоит в пути запроса, поэтому журнал сети заменяет его на
`/bot…/`, логгеры `httpx` в процессе бота — WARNING, ошибки проходят через
`без_токена`.

**Поток в Telegram — правками одного сообщения.** Заготовка «⏳», комментарий
SSE `: очередь N` → «впереди N», куски текста → правка не чаще раза в 1,5 с и
только при изменении (ворота 0: 40 правок подряд без 429 от Telegram), итог —
с подписью модели, токенов и времени; длиннее 4000 символов — продолжение
новым сообщением.

**Маска ПД — перед выходом наружу.** `agent/service/pd.py` — шаблоны Дня 29
(теперь общие с `optbench`) и маска: составные шаблоны раньше одиночных,
отчество вместе с именем, фамилия от основы целым словом. Ответ, источники и
цитаты маскируются по отдельности, затем весь текст проверяется ещё раз — если
шаблоны что-то находят, ответ не отправляется.

**Журнал бота — белый список.** `Журнал` получил параметр `поля`: у сервиса —
прежний набор, у бота — свой (кто, что, код, токены, время, правки, повторы,
скрыто ПД). Поле не из списка в файл не попадает, поэтому текст вопроса туда
не попадёт и по ошибке.

**Параметры — конфигурацией, а не аргументами.** Вызов модели в ответе RAG
проходит пять функций (`Отвечатель → _вызвать → Client.call → _call_ollama →
ollama_payload`). Конфигурация ставится контекстной переменной и читается в
двух местах: в теле запроса (опции и тег весов) и в адресе сервера. Она
действует только на свою модель — разбор реплики на 1.7B в том же ходе чата
её не получает. Без конфигурации тело запроса байт в байт как в Дне 28.

**Один источник параметров у `loc-rag-docs`.** Опции запроса перекрывают
`PARAMETER` модельфайла. Поэтому у модели в каталоге есть ссылка на
конфигурацию «после», и клиент шлёт её опции сам, а `--создать-модель` пишет те
же значения в `PARAMETER` — для `ollama run` и других клиентов.

**Честный замер на загруженном ноутбуке.** Ollama держит кэш промпта в
раннере: смена шаблона или предела на том же раннере не вызывает загрузку, и
«после» выиграло бы за счёт кэша. Поэтому модель загружается отдельным пустым
запросом с теми же параметрами загрузки, отвечает и выгружается — после того,
как фоновый поток снял показания `/proc`. Скрининг показал, что время ответа на
трёх вопросах — шум (тождественные конфигурации расходились на ±30 %: 15
конфигураций одного вопроса шли 45 минут под меняющейся нагрузкой). Отсюда
парное сравнение, детерминированные показатели (токены, память, качество) и
микрозамер скорости с тугой каруселью; порог скорости взят вдвое выше шума
контрольной конфигурации.

**Сервер Ollama без правки службы.** Переменные `OLLAMA_FLASH_ATTENTION` и
`OLLAMA_KV_CACHE_TYPE` действуют на весь сервер. Служба работает от
пользователя `ollama`; второй сервер от нашего пользователя на :11435 читает
те же модели (`OLLAMA_MODELS`, `OLLAMA_NOPRUNE=1`). В памяти — одна 4B: перед
загрузкой на одном сервере всё выгружается на другом.

**Модель без визуального проектора.** У `qwen3.5:4b` в модельфайле две строки
`FROM`: веса и проектор `mmproj`. Modelfile с одной первой строкой даёт ту же
модель для текста на 650 МБ легче и с более быстрой загрузкой.

**Проверка вне набора и вето.** Скрининг идёт на трёх вопросах, прогон
качества — на четырнадцати, и оба могут не увидеть провал на вопросе другого
вида. Короткий шаблон «договоры» прошёл оба, а на вопросе о двух договорах сразу
(так модель разбора иногда переписывает реплику чата) отвечал «не знаю». Правило
выбора получило вето: рычаг из `local-opt.json` → «вето» отклоняется с причиной
и фактами проверки, а сама проверка стала постоянной частью `check_optimize.py`.
Шаблон остаётся рычагом скрининга и конфигурацией «р-шаблон», в «после» — общий.

**Профиль вместо флага.** Локальные параметры (кросс-энкодер 8 → 2, порог «не
знаю» 0,015 под его шкалу, лучшее окно) в Дне 27 включал глобальный флаг
офлайна. Сравнение же идёт в одном процессе в облачном режиме: облачному
участнику нужна сеть, а локальные должны получить свои параметры. Поэтому
параметры собраны в `ПрофильRAG` и передаются явно; без профиля в офлайне
действует локальный (ровно то, что делал флаг), иначе — поведение Дня 24.
Тесты Дней 23–27 прошли без правки ожиданий.

**Один поиск на троих.** У `лок-4b`, `лок-1.7b` и `облако-тот-же` поиск и
лучшие окна выполняются один раз, и готовый отбор получают все трое. Так у них
одинаковые фрагменты и одно решение порога «не знаю», а различаются они только
генерацией. `облако-лучшее` ищет само — «фильтр» Дня 24 с LLM-реранкером
облака: это сравнение системы с системой.

**Новый вопрос и повтор.** Повтор 1 не читает кэш оценок кросс-энкодера (но
пишет его), и промпт модель видит впервые. Повторы 2–3 идут с живыми кэшами.
Вектор вопроса и лучшие окна не кэшируются вовсе. Попадание в кэш промпта
Ollama по счётчику не видно: `prompt_eval_count` при попадании тот же (проба:
354 → 354), меняется только время чтения (43,9 → 0,84 с у 4B). Поэтому промпт
считается взятым из кэша при скорости чтения от 100 токенов в секунду (без
кэша 4B читает 7–16, 1.7B — 25–40).

**Сеть каждого ответа.** `offline.снимок_журнала()` до и после ответа даёт его
сеть: у локальных участников внешних запросов 0 в каждом ответе — и в
смешанном прогоне, где рядом работает облако. Облачные участники в том же
журнале видны с внешними запросами, значит, ноль у локальных настоящий.

**Температура ответа — из карты ролей.** Прогон сравнения вскрыл, что ответ
RAG шёл при температуре клиента (0,2), хотя `local-roles.json` объявлял для

httpx.HTTPTransport ────── перехватчик (offline.py): журнал каждого запроса процесса;
                              в офлайне нелокальный адрес → ОшибкаОфлайна (наследник ConnectError)
MCP: Server.готов          ── в офлайне «наружу» (http не на этой машине, npx/uvx, «сеть»: true) → не готов
     Session.окружение_процесса() → AGENT_OFFLINE, LOCAL_ROLES, HF_HUB_OFFLINE дочерним серверам
поиск «фильтр/полный»      ── в офлайне второй этап из карты: кросс-энкодер, K_до 8 → 2, порог «не знаю» 0,015
ответ с цитатами           ── в офлайне фрагмент → лучшее окно кросс-энкодера (≈ 450 токенов)
чат                        ── разбор на 1.7B по схеме + поправки кода; этапы хода с секундами и токенами
агент с инструментами      ── «облегчённый»: сжатый промпт, без проверки самоотчёта и судьи (карта, «агент»)
```

**Почему приложение — сам агент.** Задание дня — интегрировать локальную
модель в приложение. У проекта приложение уже есть: агент с консолью и
страницами. До Дня 27 локальная модель была одним из провайдеров каталога, и
выбранная в чате, она отвечала пользователю — но разбор реплики, переписывание
и LLM-реранкер по-прежнему уходили в облако. Офлайн-режим переводит на
локальные модели **все** 14 ролей агента разом, через одну точку —
`catalog.for_role`, — поэтому ни один путь агента не нужно переписывать.

**Доказательство «без облака» — три слоя.** Не позвать облако мало: важно
показать, что позвать его было нельзя. (1) Ключи облачных провайдеров вычищены
из окружения процессов: пустое значение `.env` не перебивает. (2)
Предохранитель в `Client.call` отказывает облачной модели до открытия сокета.
(3) Перехватчик на транспорте httpx видит каждый HTTP-запрос процесса — свой
клиент LLM, эмбеддинги Ollama, MCP по HTTP, `huggingface_hub` — и в офлайне
блокирует нелокальный адрес. Журнал ведётся всегда: в облачном режиме он
показывает внешние запросы, в офлайне их ноль. Тестовый `MockTransport` —
другой класс, перехватчик его не касается.

**Карта ролей (`local-roles.json`).** Выбор пользователя: служебные роли —
маленькая `qwen3:1.7b`, ответ и инструменты — основная `qwen3.5:4b` (замер Дня
26). Проба на шести типовых репликах чата подтвердила выбор для разбора:
`qwen3:1.7b` с полным промптом Дня 25 — 5 из 6 верно за ≈ 50 с, `qwen3.5:4b`
— 4 из 6 за ≈ 150 с; короткий промпт с примерами маленькую модель ухудшил (2
из 6). У каждой роли — схема ответа (`format` в Ollama), температура и предел
длины; окно контекста — одно на всех: смена `num_ctx` между вызовами
перезагружает модель. Карту читает и показывает `--офлайн-статус` и карточка
«Офлайн-режим» на `/local`.

**Схемы ответа (`agent/local/schemas.py`).** Ollama ограничивает генерацию
JSON-схемой: маленькая модель физически не может начать ответ с рассуждения
или забыть кавычку. Кириллические имена полей работают. Схема не проверяет
смысл — смысл по-прежнему проверяет код.

**Поправки кода для разбора локальной модели.** Обе локальные модели не
записывали цель из «Мне нужно сравнить… Начнём с…», а маленькая ещё и
переписывала в «вопрос для поиска» кусок инструкции («Назови договор,
оператора, статью бюджета») и складывала пересказ цели в ограничения. Код
берёт цель из явного «мне нужно / помоги / хочу» в начале предложения, ищет по
реплике, если вопрос дословно стоит в инструкции, и отбрасывает ограничения,
если в реплике нет признака правила ответа. Каждая поправка видна в ходе
(«↳ поправка кода: …»).

**Поиск в офлайне.** LLM-реранкер на 20 фрагментах — это минуты на CPU,
поэтому в офлайне второй этап делает кросс-энкодер bge-reranker (ONNX, уже
скачан). Шкала его оценок другая: верный фрагмент получает 0,02–0,1, и порог
«не знаю» Дня 24 (0,5) отправил бы в «не знаю» всё. `--офлайн-подбор` на
стенде вопросов Дня 21 (оценки в кэше индекса) выбрал K_до 8 (нужный фрагмент
в двух фрагментах промпта у 22 из 24 вопросов, как при K_до 10, но быстрее) и
порог 0,015 (ловушки 4 из 5, лишних «не знаю» 0). Порог косинуса — свойство
эмбеддера, он остаётся как в режиме.

**Почему фрагмент — лучшее окно.** 4B читает промпт ≈ 7 токенов в секунду, а
раздел договора целиком — 2–3 тысячи символов. Кросс-энкодер оценивает
длинный чанк окнами по 512 токенов; в офлайне модели отдаётся лучшее окно, и
цитаты проверяются по нему же. Промпт ответа — с 2419 до ≈ 2000 токенов.

**Кэш промпта и архитектура модели.** У `qwen3:1.7b` повтор того же начала
промпта стоил 0,1 с на чтение — Ollama держит его в кэше. У `qwen3.5:4b`
гибридная память (часть слоёв хранит рекуррентное состояние), и llama.cpp
внутри Ollama не умеет отрезать её кэш на общем начале: журнал службы пишет
«forcing full prompt re-processing… hybrid/recurrent memory». Восстановить
можно только сохранённые точки — около конца прошлых промптов. Поэтому новая
реплика чата читает промпт целиком (≈ 14 токенов в секунду, 1159–2148 токенов
за 83–156 с), второй круг инструментов — только новое (продолжает свой же
промпт: 419 токенов из 2252), а точный повтор промпта — 4 токена за 0,7 с
(«restored context checkpoint»). Это главная статья времени на этой машине и
задел для следующего дня — оптимизации локальной модели.

**Облегчённый агент (выбор пользователя).** Промпт агента с инструментами — ≈ 4
тысячи токенов (инварианты с обоснованиями, профиль, рамки проекта, знания,
решения, правила инструментов), и вопрос о задаче трекера шёл 21 минуту: два
круга по 5–6 минут и три повтора из-за проверки самоотчёта. В офлайне промпт
сжат (рамок и решений нет, инварианты — кодом и правилом, знания — до двух и
только по словам запроса, правила инструментов — вчетверо короче), проверка
самоотчёта и судья по смыслу по умолчанию выключены — раздел «агент» карты,
флажки на `/local`, `--офлайн-агент`. Тот же вопрос — 7,9 минуты. Окно истории
агента в этом режиме — как у чата: 4 последних сообщения по 400 символов, а в
коротких правилах инструментов — «данные о задаче бери из вызова в этом ходе,
а не из истории». Без этого 4B с длинной историей стенда (20 сообщений, в том
числе ответ о другой задаче) ответила о MIG-8 статусом MIG-2, не вызвав
инструмент, а на повторе написала «запросил список задач» без вызова.

**Ход по этапам (`agent/local/progress.py`).** Наблюдатель — контекстная
переменная, а не аргумент через все слои: чат, агент и клиент LLM сообщают о
себе, а кто хочет видеть ход, ставит наблюдателя на время операции. Клиент,
увидев наблюдателя, зовёт Ollama потоком и сообщает счётчик токенов. Страница
получает события NDJSON-ручкой (`/api/chat/say`, `/api/ask` с `stream`),
консоль — строкой на месте в терминале.

```

catalog.get(ключ) ─────┤

**Локальная модель — провайдер каталога, а не отдельная система.** У
`Model` флаг `local`: ключ не нужен (`has_key` — истина, `api_key` — пусто),
цена 0, «скачана ли» знает только Ollama (`installed()` спрашивает `/api/tags`
одним запросом на весь каталог с кэшем в 20 с — кэшируется и отказ, иначе без
Ollama страница ждала бы по 2 с на модель). Всё, что зовёт модель через
`Client.call(ключ, …)`, — ответ агента, RAG Дней 22–24, чат Дня 25, роли
каталога — работает на локальной модели без правок: `--модель loc-qwen17`.

**Почему родной `/api/chat`, а не OpenAI-совместимый `/v1`.** Тот же протокол,
что у облака, был бы проще, но у него два изъяна для агента. Окно контекста
по умолчанию у Ollama — 4096 токенов, лишнее она обрезает **молча**, а через
`/v1` окно не задаётся (только Modelfile или переменная службы). RAG-промпт Дня
24 — 3–6 тысяч токенов. В родном API окно (`options.num_ctx`) и длина ответа
(`num_predict`) задаются на запрос, «размышления» выключаются `think: false` и,
если их включить, приходят отдельным полем `thinking`, а в ответе есть замеры
самой Ollama: загрузка модели, чтение промпта, генерация. Разницу протоколов
клиент закрывает сам: аргументы вызова инструмента — объект, а не строка,
ответ инструмента называет его по имени (`tool_name`), теги `<think>` в тексте
вырезаются. Снаружи — тот же `Reply`, тот же `LLMError`, а ошибки Ollama
переведены в понятные: «не скачана — ollama pull …», «не умеет инструменты»,
«не отвечает — systemctl start ollama».

**Одинаковый замер для локальной и облачной.** У Ollama есть серверные замеры,
у облака — только итог, поэтому сравнение идёт потоком (`stream.py`), и время
до первого токена и ток/с клиент считает сам — для обеих одинаково. Скорость
считается только по ответу не короче 5 токенов: облако присылает короткий
ответ одним куском, и по «Париж» выходил то 0, то сотни токенов в секунду —
вместо этого «—». Серверные замеры Ollama показываются рядом: по ним видно,
что съело время.

**Что показал CPU этой машины.** i3-1005G1 — 2 ядра, 4 потока, без видеокарты,
под чужой нагрузкой и с полной подкачкой. Модель 4B читает промпт 6–7 токенов в
секунду и генерирует 1–3; первая загрузка весов в память — около 20 с; ответ по
документам с тремя фрагментами (3266 токенов) шёл 19 минут. Отсюда решения:
- `LOCAL_TIMEOUT` 1800 с (вызов без потока ждёт ответ целиком);
- `keep_alive` 30 минут (иначе модель выгружается между вопросами);
- после своих задач замер выгружает модель (две 4B разом — подкачка);
- маленькая `qwen3:1.7b` добавлена в кандидаты (выбор пользователя), а задача
  по документам в замере — с одним фрагментом;
- у задач свой предел длины ответа и общая системная подсказка «отвечай
  коротко; число — только числом»: без неё Qwen на «ответь числом» пишет сотни
  токенов рассуждений, то есть минуты.

**Окно контекста и перезагрузка.** CLI и `/v1` работают с окном Ollama по
умолчанию (4096), клиент агента — с 8192. Модель, загруженная с одним окном,
при запросе с другим загружается заново (≈ 4 с у 1.7B, ≈ 20 с у 4B). Поэтому
сырые HTTP-примеры окна не задают и делят загрузку с CLI.

## Мини-чат с RAG и памятью задачи (День 25)

```
реплика ──▶ разбор реплики (модель роли «разбор-реплики», отдельный вызов)
               вход: память задачи без «выяснено» + 6 последних сообщений + реплика
               выход JSON: вид · вопрос для поиска · подвопросы · цель · уточнения ·
                           ограничения · термины
               │
               ├──▶ слияние в память задачи (код, state.py) ─▶ memory/chat/chat-<имя>.json
               ├──▶ реплика в историю (короткая память, сессия «чат:<имя>») ─▶ dialog.db
               │
        ┌──── вид ────┐
   документы       разговор
        │               │
  поиск «фильтр»   поиск «фильтр» (найденное показывается рядом, в ответ не идёт)
  по вопросу или        │
  по подвопросам   ответ по памяти задачи: JSON {ответ, опора: [Ц, О1, В3…]}
  со слиянием           │ код: коды опоры есть в памяти, числа ответа — в записях опоры
        │               │ нарушение → один повторный запрос
  ответ Дня 24 с        │
  контекстом разговора  └──▶ источники: записи памяти, у «В» — их документы
  перед фрагментами
        │
  источники: документы с chunk_id и цитатами; у «не знаю» — проверенные разделы
  подтверждённый ответ ─▶ «выяснено» (В)
```

**Память задачи — отдельно от истории.** Короткая память Дня 11 отдаёт в промпт
хвост в шесть сообщений: к десятой реплике первая — та, где названа цель, —
из окна уже выпала. Поэтому цель, уточнения, ограничения и термины лежат в
своём JSON и идут в промпт целиком на каждом ходе, а история нужна только для
местоимений и «а у них?». Рабочая память Дня 11 (`working.py`) для этого не
годится: она — про задачу миграции со стадиями и подписью под планом, а здесь
нужна память разговора.

**Модель извлекает, код сливает.** Разбор реплики возвращает только новое из
этой реплики; правила слияния — в коде: цель ставится один раз, а меняется
лишь явной сменой (`смена_цели`), прежняя сохраняется; повтор уже записанного
не дублируется; термин с новым значением заменяет старый и помнит прежнее;
уточнение, которое лишь пересказывает цель, не записывается. Иначе цель
«дрейфует»: модель на каждой реплике пересказывает её чуть иначе. «Выяснено»
пишет только код — из ответа, у которого есть подтверждённые цитаты.

**Почему разбор — отдельный вызов, а не часть ответа** (выбор пользователя).
JSON ответа Дня 24 и так большой, а при «не знаю» по порогу модель ответа не
зовётся вовсе — память задачи тогда не обновилась бы как раз на реплике, где
человек уточняет, что имел в виду. Цена — короткий вызов на каждую реплику.

**Поиск по самостоятельному вопросу.** «А у ВымпелКома?» и «по нему» ищутся
как вопросы с именем договора. Два урока живых прогонов вошли в промпт разбора:
не дописывать из цели то, без чего вопрос ясен («в бюджете ИТ на 2026 год» —
реранкер ставил верному фрагменту 0,3 вместо 1,0, и включалось «не знаю»), и
заменять термин пользователя его значением («срок уведомления» → «за сколько
дней обязан предупредить» — иначе находился не тот раздел договора). Вопрос
сразу о двух договорах раскладывается на подвопросы: по составному вопросу
реранкер высоко ставит только один пункт, и второй договор терялся. Отборы
подвопросов сливаются по очереди — лучший фрагмент каждого идёт в промпт
первым, — а в ответ уходят все подвопросы.

**Контекст разговора — не источник фактов.** В промпт ответа по документам
перед фрагментами ложатся память задачи и последние реплики с правилом
«понять вопрос и соблюсти ограничения, а факты, числа и цитаты — только из
фрагментов». Числа из слов пользователя (его ограничения, термины, реплика)
цитаты не требуют, числа из прошлых ответов — требуют: «выяснено» в этот
промпт не идёт.

**Источники всегда** (выбор пользователя: «память или документ»). Вопрос о
самом разговоре («какая у нас цель?», «сведи итог») отвечается по памяти
задачи; модель ссылается на записи кодами, код проверяет, что каждое число
ответа стоит в записи опоры, и подставляет документы записей «В». У «не знаю»
источники — проверенные разделы. Ответа без блока источников не бывает, и это
проверяется на каждом ходе сценариев.

**Проверка — заданные сценарии, код и судья** (выбор пользователя). Два
сценария (`chat-scenarios.json`, 14 и 13 реплик) с ожиданием на каждой
реплике: вид, факты, документ, что записать в память, ловушка. На каждом ходе
код проверяет поиск, источники, документ с цитатой, факты, память и то, что
цель не изменилась; в конце судья читает весь разговор. Сценарий идёт в своей
сессии с чистого листа, поэтому прогоны сравнимы.

## Цитаты, источники и «не знаю» (День 24)

```
  Отвечатель.ответить(вопрос, «rag», поиск=«фильтр», формат=«цитаты»)
        │                                   ← cli.py --с-цитатами / --rag, /api/rag/cited,
        ▼                                     MemoryAgent.ответ_по_документам, check_citations.py
  Поисковик.найти → Отбор (оценки LLM-реранкера у кандидатов)
        │
  abstain.решить(отбор, порог)   уверенность = лучшая оценка реранкера
        ├─ ниже порога ──▶ «не знаю» (решил порог): в промпт НИЧЕГО не идёт;
        │                   abstain.уточнить: модель видит вопрос и названия
        │                   ближайших разделов → один уточняющий вопрос
        ▼
  собрать_сообщения(…, ЦИТАТЫ): правила cite.ПРАВИЛА_ЦИТАТ + фрагменты [n]
  модель → JSON {ответ, источники: [n], цитаты: [{n, текст}], не_знаю, неоднозначно, уточнение}
        │
  cite.разобрать → cite.проверить_цитаты(тексты фрагментов)
        │   дословно | почти (≥ 90 %, шум OCR) | в другом фрагменте (номер исправляется)
        │   | слишком короткая | не найдена
  cite.нарушения: нет ответа / источников / цитат, чужие номера, цитата не найдена,
        │         число ответа без цитаты (по значению, без чисел из вопроса)
        ├─ есть нарушения ──▶ один повторный запрос: модели — её JSON и список нарушений
        ├─ «не_знаю» от модели ──▶ «не знаю» (решила модель) + её уточнение
        ├─ нет ни одной подтверждённой цитаты ──▶ «не знаю» (решила проверка цитат)
        ▼
  ОтветRAG: текст, источники (паспорт по номеру: файл, раздел, пункт, стр., chunk_id),
            выдержки (цитаты с отметкой проверки), решение (уверенность, порог)

  agent/rag/citecheck.py  10 контрольных (rag-control.json) + 4 расплывчатых
     (rag-vague.json) × формат «цитаты» и «текст» Дня 23:
     источники · цитаты · подтверждено · числа ответа в цитатах · смысл (код + судья)
     · «не знаю» с уточнением → RAG-CITATIONS.md + index/citations.json
```

**Почему JSON, а паспорт подставляет код.** Модель называет только номера
фрагментов; файл, раздел, страницы и `chunk_id` берутся из индекса по номеру.
Выдумать источник модели нечем, а «источник» ответа — это всегда реальный чанк.
Неразобранный ответ не выдаётся — он идёт в повторный запрос.

**Почему цитату проверяет код, а не судья.** «Есть ли этот текст в документе» —
вопрос, на который у кода точный ответ. Нормализация прощает регистр, ё,
кавычки, пробелы и переносы OCR; 90 % сходства — шум скана, ниже — уже
пересказ. Судья нужен для того, чего код не видит: следует ли ответ из цитат
по смыслу. Код при этом проверяет то, что может: каждое число ответа должно
стоять в подтверждённой цитате. Первый же прогон показал зачем: модель
цитировала сумму, а в ответ добавляла НДС и период из того же фрагмента, и
судья ставил «частично». После правила «ответ не шире цитат» и повторного
запроса — 8 из 8 «да». Цифры, приклеенные к буквам («УИС-5», «ВОГ396658»,
«V2»), — часть названия, а не факт: иначе ответ «в листе «УИС-5»» требовал бы
цитаты на «5». Условия без чисел («без НДС») код не сверяет — это остаётся
судье.

**Почему «не знаю» решает порог в коде.** Правило в промпте «не угадывай»
держится не всегда, а косинус ловушку не отличает (Дни 22–23). Лучшая оценка
LLM-реранкера отличает: на стенде Дня 21 у вопросов с ответом она не ниже 0,5,
у ловушек — 0. Ниже порога модель не получает фрагментов вовсе — отвечать по
документам ей нечем, — а уточняющий вопрос пишет по названиям ближайших
разделов. Порог подбирается (`abstain.подобрать`): сначала без лишних «не
знаю» на вопросах, где нужный фрагмент найден, затем больше честных «не знаю»
(ловушки и слабый контекст), затем осторожнее.

**Почему у модели свой путь к «не знаю».** Расплывчатый вопрос «А сколько это
стоит?» порог не ловит: цены в договорах есть, и реранкер ставит им 0,8. Ловит
правило промпта: не назван предмет, а фрагменты отвечают по-разному — «не
знаю» и уточнение с вариантами (названия, без сумм). Кто решил — порог, модель
или проверка цитат — пишется в ответ и в отчёт.

**Почему в «не знаю» нет ссылок и цифр.** У такого ответа нет источников, и
ссылкам [n] не на что указывать; цифра в уточнении была бы ответом без
проверки. Код вырезает [n] из уточнения, промпт просит варианты словами.

## Второй этап поиска: реранкинг, фильтр и rewrite (День 23)

        │                                              --сравнить-поиск; /api/rag/select,

     сетка           rewrite × реранкер × K_до {10,20} × K_после {3,5,8} × порог {0…0,7}
                     без единого нового вызова — срезы тех же списков
     выбрать         полнота с допуском в один вопрос стенда → MRR → пустой контекст
                     у ловушек → меньше фрагментов; среднее без rewrite и с ним
     записать        rag-settings.json (выбранное) + index/calibration.json + RAG-RERANK.md

  agent/rag/qa.py  прогнать(…, режимы=без, база, фильтр, rewrite, полный) → RAG-QA.md

**Почему три реранкера, а не один.** Лекция недели называет компромисс
«точность против задержки», и его надо было измерить, а не принять на веру.
Кросс-энкодер — родной к bge-m3 и локальный (документы не покидают машину), но
на CPU это секунды на вопрос. LLM понимает русский и быстр, но это вызов облака
с фрагментами документов. Эвристика ничего не стоит и служит нижней планкой и
запасным путём. Все три за одним интерфейсом (`Реранкер.оценить`) и все
приведены к [0, 1] — только тогда один порог имеет смысл.

**Почему порог подбирается, а не ставится.** Абсолютные оценки кросс-энкодера
плохо откалиброваны: верному пункту о сроке оплаты он дал 0,06 при правильном
порядке, а ловушке — 0,34. Порог «на глаз» резал бы верное. Поэтому подбор идёт
сеткой, а правило выбора ставит полноту первой: фильтр, который выбрасывает
ответ, хуже никакого.

**Почему у полноты допуск в один вопрос.** Первый подбор шёл по строгому
правилу, и оно выбрало эвристику: она нашла на один вопрос из 24 больше, чем
LLM-реранкер и кросс-энкодер, но почти не фильтровала — 7,2 фрагмента в
промпте, ловушки проходили в 90% случаев, MRR 0,65 против 0,83. Один вопрос
на стенде из 24 — шум стенда, а не качество, и строгое правило отдавало победу
тому, кто меньше режет. Решение о допуске принял человек, посмотрев оба итога;
правило применяется и к сохранённой сетке `index/calibration.json`
(`calibrate.свести`) без пересчёта.

**Почему LLM-реранкер видит чанк целиком.** Живой прогон на c03 показал, что
выбранный LLM-реранкер ставит верному фрагменту 0 из 10: ради экономии он видел
первые 1500 символов, а пункт 2.2.7 стоит на 2259-м. Так обрезалась треть
чанков «структуры» (153 из 459). После исправления подбор пересчитан (оценки
кросс-энкодера — из кэша), и LLM-реранкер выиграл уже по любому правилу:
K 20 → 8, порог 0,3, полнота 0,98, MRR 0,89, 3,1 фрагмента, все ловушки без
контекста.

**Почему кросс-энкодер оценивает окнами.** У него та же беда в другой форме:
пара «вопрос + текст» — до 512 токенов, а с вопросом не влезают 352 чанка
«структуры» из 459 (медиана — 589, максимум — 1175). Хвост модель не видела, и
у c03 верный чанк был девятым с 0,005. Выбор человека из трёх вариантов (окна,
длина пары 1024, короче чанки) — окна: чанк режется по 512 токенов с
перекрытием 128, паспорт чанка идёт в каждое окно, оценка чанка — лучшее окно.
Модель остаётся на привычной длине, индекс Дня 21 не меняется. Цена — ≈ 1,7
пары на чанк: 96 с на новый вопрос вместо 34. Схема окон — в ключе кэша, чтобы
оценки обрезанных пар не подмешивались. С окнами c03 — второй (0,376), на
подборе MRR 0,86 вместо 0,83, но LLM-реранкер (0,89, ловушки без контекста)
по-прежнему основной.

**Почему подбор не на контрольных вопросах.** На десяти вопросах Дня 22
сравниваются режимы. Подобрать порог на них же значило бы подогнать результат;
стенд подбора — 24 вопроса и 5 ловушек Дня 21 (`rag-questions.json`).

**Почему реранкер смотрит на исходный вопрос.** Переписанные запросы расширяют
поиск, но могут увести смысл (так и было: один из запросов c03 ушёл в сторону).
Оценка «помогает ли фрагмент ответить» считается по тому, что спросил человек.

**Почему кэши в базе индекса.** Кросс-энкодер считает ≈ 1,5 с на пару, а подбор,
контрольные вопросы и показ задают одни и те же пары. Переписанные запросы
кэшируются по той же причине и ещё по одной: сравнение режимов не должно мерить
разброс модели от прогона к прогону. Кэш лежит в `docs.db` и уезжает с копией
индекса на стенд показа и в чек-лист.

**Где граница кода и модели.** Модель переписывает запросы (и, если выбран
LLM-реранкер, оценивает фрагменты); всё остальное — код: слияние, пороги, K,
судьба каждого кандидата. Сбой реранкера не валит ответ: поиск идёт по первому
этапу, а в `Отбор.ошибки` и на этапе «реранк» честно записано, что второго этапа
не было.

**Почему ответ по документам — не `MemoryAgent.ask`.** Обычный ответ собирается
из слоёв памяти, стадии задачи и инвариантов миграции ГИС и проверяется

документов — свой короткий промпт, но метод агента: он пишет обмен в короткую

**Где граница кода и модели.** Модель отвечает и судит; код решает всё, что
можно проверить без неё: какие фрагменты ушли в промпт, на какие [n] сослался
ответ и существуют ли они, есть ли в ответе нужный факт, есть ли его числа во
фрагментах. Вердикт судьи код поправляет только в двух случаях, где у судьи нет
данных (он не видит фрагментов) или он нарушил своё же правило.

## Индекс документов (День 21)

```
  agent/rag/

                   PDF: pdftotext постранично; страница < 80 букв → pdftoppm + tesseract
                        (кэш index/ocr/<sha1>-<стр>.txt); колонтитулы — строки с половины страниц

    chunking.py  нарезать(документ, стратегия) → [Чанк + паспорт]

                   «структура»: группа блоков с одним путём раздела; > макс — по абзацам;

    embed.py     ЭмбеддерOllama (HTTP /api/embed, пачки по 16) | ЭмбеддерХэш — L2-нормировка
    store.py     ХранилищеИндекса: SQLite index/docs.db
                   индексы(стратегия, эмбеддер, размерность, параметры, …)
                   документы(стратегия, источник, …) · чанки(chunk_id, …, вектор BLOB f32)
                   кэш_векторов(модель, хэш текста, вектор)
                   искать(): матрица стратегии в памяти → матрица @ запрос → argsort
    indexer.py   Индексатор: извлечь → нарезать → векторы (кэш, запись каждые 64) → записать
    evaluate.py  статистика нарезки + эталонные вопросы (hit@k, MRR) → RAG-COMPARISON.md

  cli.py --извлечь | --индексировать | --индекс | --найти-в-документах | --чанк | --сравнить-стратегии
  web.py  /rag  + /api/rag, /api/rag/build (фон), /api/rag/search, /api/rag/chunk/<id>, /api/rag/compare (фон)
  rag_server.py  MCP «docs»: search_docs, compare_strategies, get_chunk, list_documents, index_stats
```

**Почему индекс не часть памяти агента.** Память — то, что агент узнал в
разговоре и решил запомнить; она пишется по ходу работы и маршрутизатором
реплик. Индекс — внешний корпус, который собирает человек: минуты OCR и час
эмбеддингов, а не запись в JSON. У них разные хозяева, разный ритм и разное
хранилище, поэтому индекс — отдельный пакет со своим файлом, а агенту он
отдаётся тем же путём, что и внешние системы, — MCP-сервером. Маршрутизатор Дня
20 выбирает `docs` по темам, как любой другой сервер.

**Почему обе стратегии в одном файле.** Сравнение читает их разом, а вектор
запроса считается один раз на обе — разница в результатах получается только от
нарезки. Строки разведены полем `стратегия`: пересборка одной стратегии —
транзакция, которая не трогает другую.

**Почему SQLite, а не FAISS.** Весь проект хранит своё в SQLite; тысяча чанков
по 1024 числа — это 4 МБ, и умножение матрицы на вектор занимает миллисекунды.
FAISS окупается на сотнях тысяч чанков и встанет за тот же метод `искать`.

**Где проходит граница кода и модели.** Эмбеддер — модель; всё остальное —
код: извлечение, резка, паспорт, сравнение. Поэтому сравнение воспроизводимо:
при том же индексе и тех же вопросах метрики не меняются от запуска к запуску.

## Схема

```
   запрос пользователя
        |
        +--> ScenarioStore.match()   сработал триггер сценария?
        |         |
        |         да ──> ScenarioRunner: шаг за шагом
        |                   каждый шаг: своя роль, своя модель, своя стадия
        |                   результат шага -> рабочая память -> вход следующего
        |         нет
        v
  +-----------------+
  | StateValidator  |     рубеж 1: запрос требует нарушить инвариант? — кодом
  | check_request   |---> да: отказ; ни Router, ни модель не зовутся (День 16)
  +-----------------+
        |
        v
  +-----------------+     правило 5: разбор реплики
  | MemoryManager   |---> Router (дешёвая модель) -> профиль / знания / решения
  | единая ЗАПИСЬ   |     правило 2: реплика -> краткосрочная
  +-----------------+     правило 3: шаг задачи -> рабочая
        |                 правило 4: завершение -> решения, рабочая очищается
        |                 правило 1: явное указание -> куда сказано
        v
  +-----------------+
  | PromptBuilder   |     единое ЧТЕНИЕ: отбор по стадии задачи
  | + трейс         |     блоки: настройки пользователя | рамки проекта | ...
  +-----------------+
        |
        v
  +-----------------+
  | llm.Client      |     единственное место, где происходит HTTP-запрос
  +-----------------+
        |
        v
  +---------------------------+
  | StateValidator            |  инварианты — кодом, блокируют ответ
  | PreferenceChecker         |  предпочтения — кодом, заставляют переписать
  +---------------------------+
        |
        +--> строка «ПЕРЕХОД: <стадия>» в ответе?
        |         |
        |         да ──> Ворота: стрелка? условие? ──> переход или отказ,
        |                 попытка ложится в журнал задачи в любом случае
        v
    ответ + трейс + проверка профиля + расход + судьба просьбы о переходе
```

## Инварианты

Отдельный модуль (`agent/invariants.py`) и отдельный файл на уровне проекта.
Раньше инварианты лежали разделом профиля — и это был изъян: профиль принадлежит
человеку, а инварианты проекту, поэтому переключение пользователя меняло набор
запретов.

```
вид       стек | архитектура | решение | бизнес-правило | безопасность
тип       запрет-слов | запрет-в-коде | запрет-регулярок | смысловой
уровень   проектный (memory/invariants.json) | личный (профиль)
почему    обоснование — идёт в текст отказа
вместо    допустимая альтернатива — тоже идёт в отказ
```

Поля `почему` и `вместо` не украшение: **отказ формирует код**, а не модель, и
берёт их оттуда. Поэтому отказ одинаков при каждом конфликте и содержит то, с
чем можно спорить по существу. Жёсткий инвариант без значений отклоняется при
заведении: непроверяемый запрет хуже отсутствующего — он создаёт ложное чувство
защиты.

Тип «мягкий» из прежних дней упразднён. Он означал «в промпт просьбу положим, а
проверять не будем», то есть инвариантом не был. Именно такими были бизнес-правило
про 1С и архитектурное решение про WMS/WFS.

## Три рубежа проверки

```
запрос ──► check_request()      требование нарушить? отказ до обращения к модели
                                 вопрос об инварианте — не нарушение
   │
   ▼
ответ ──► check()               слова, вызовы API в коде, выражения — кодом
   │                             в объяснении проза не проверяется, код — да
   ▼
смысл ──► check_self_report()   агент назвал применимые инварианты сам?
      └─► judge()               дешёвая модель судит по сути
```

Первый рубеж детерминирован, но проверяет лишь упоминание; второй понимает
смысл, но недетерминирован. Порознь каждого мало.

Проверяющей модели намеренно не показывают ни запрос пользователя, ни переписку:
она видит только правила и готовый ответ. Уговаривать её нечем.

Ответ, оставшийся нарушенным после всех попыток, **заменяется отказом** и в
диалог попадает уже отказом. Сам текст остаётся в `Answer.usage`/трейсе — для
разбора, но не для пользователя.

## Ворота перехода

Стадию задачи меняет единственное место — `agent/transitions.py:Ворота`. Через
него идут все: команда человека, строка `ПЕРЕХОД: <стадия>` в ответе модели, шаг
сценария и служебная свёртка задачи.

```
Ворота.проверить(state, куда, кто) -> Вердикт        ничего не меняет
Ворота.перевести(state, куда, кто) -> Вердикт        меняет и пишет след
Ворота.обзор(state)                -> все стадии     этим живут кнопки и CLI
Ворота.маршрут(откуда, куда)       -> кратчайший путь по TRANSITIONS
```

Проверок две, и они разной природы:

| Рубеж | Что проверяет | Где описан |
|---|---|---|
| стрелка | есть ли такой переход в жизненном цикле | `TRANSITIONS` в `memory/working.py` |
| условие | заслужен ли шаг: подпись под планом, закрытые шаги, отчёт проверки | `БАЗОВЫЕ` в `transitions.py` + личные в файле |

Условия ворота берут **вызовом**, а не снимком: пользователь может завести своё
условие посреди работы, и следующий же переход обязан его увидеть. Ровно по той
же причине валидатор берёт вызовом инварианты.

Разделение обязанностей между модулями здесь такое: `transitions.py` знает
правила и умеет выносить вердикт, но не знает, где лежит состояние;
`memory/working.py` хранит следы, по которым условия проверяются (подпись под
планом, отчёт валидации, журнал отклонённых попыток), но не знает правил;
`agent.py` связывает их и добавляет то, чего нет ни у того, ни у другого, —
вызов модели-ревизора и запись в журнал маршрутизации.

**Почему отказ формирует код.** Тот же довод, что и с инвариантами: текст отказа
должен быть одинаков при каждой попытке и называть конкретное условие, его
обоснование и способ его выполнить. Дополнительно отказ считает законный маршрут
до цели и вердикт по ближайшему шагу этого маршрута — без этого совет «идите
через исполнение» умалчивает, что исполнение тоже заперто.

## Состояние задачи

Формализовано тремя частями, и каждая отвечает на свой вопрос:

```
этап       stage           planning → execution → validation → done
шаг        шаги[] + текущий_шаг + источник (сценарий | план)
ожидание   ожидание        запустить | продолжить | подтвердить-переход |
                           ответ-пользователя | решение-человека | ничего
пауза      пауза + причина_паузы   — флаг ПОВЕРХ этапа, а не пятая стадия
```

Переходы между этапами ограничены таблицей `TRANSITIONS` и условиями ворот;
перечень ожиданий и перечень причин паузы тоже закрыты, и значение вне перечня
отклоняется. Смысл один и тот же: недетерминированная модель не должна иметь
возможности объявить задачу в состоянии, которого не бывает.

Три поля состояния существуют только ради ворот и заполняются не моделью:

```
план_утверждён     кто, когда, отпечаток подписанного плана
отчёт_валидации    вердикт, пункты, отпечаток проверенной работы
отказы[]           отклонённые попытки перехода: кто, куда, почему не пустили
```

Отпечатки — это способ поймать правку задним числом. Подпись относится к тому
плану, под которым её поставили, отчёт — к той работе, которую проверяли; стоит
плану или работе измениться, и ворота закрываются сами, без чьего-либо решения.

Указатель шага двигает `TaskState.закончить_шаг()`, а не исполнитель сценария.
Это не мелочь: именно запись указателя на диск и позволяет продолжить работу в
другом процессе. Пока «где мы стоим» жило в локальной переменной исполнителя,
отложенную задачу можно было только начать заново.

Ответы человека (`ответы[]`) хранятся отдельно от собранных данных
(`collected`): собранное — то, что выяснил агент, ответы — то, что сказал
человек.

## Исполнение и остановки

`ScenarioRunner` имеет два входа и один общий цикл:

```
run(сценарий, запрос)        завести задачу, заполнить шаги, пойти с первого
resume(task_id, ответ)       поднять задачу с диска и пойти с текущего шага
        \                   /
         _прогнать(...)     общий цикл: проверка паузы → переход → шаг → запись
```

Цикл останавливается в пяти местах, и все пять пишут в состояние причину и
ожидание:

| Проверка | Когда | Ожидание |
|---|---|---|
| `состояние.пауза` перед шагом | кнопка «Пауза» | `продолжить` |
| смена стадии при `по_шагам` | перед переходом | `подтвердить-переход` |
| `ПереходОтклонён` от ворот | условие перехода не выполнено | `решение-человека` |
| `ответ.blocked` | инвариант не соблюдён за все попытки | `решение-человека` |
| маркер `НУЖНЫ СВЕДЕНИЯ` | шаг сам спросил | `ответ-пользователя` |

Пятая остановка появилась вместе с воротами и действует в двух точках: посреди
прогона, когда очередной шаг требует закрытой стадии, и на финише, когда
проверка не пройдена. В обоих случаях сделанная работа остаётся в рабочей
памяти, а решение принимает человек.

Пауза проверяется **перед** шагом, а не внутри: текущий шаг всегда доводится до
конца, потому что ответ модели уже оплачен.

`resume` запоминает причину паузы до её снятия. Иначе цикл, увидев несменённую
стадию, снова просит подтвердить тот же переход — и так до бесконечности;
именно эта ошибка и была поймана прогоном.

дописываются, знания уточняются по идентификатору.

**Почему сценарии отдельным файлом, а не разделом профиля.** Профиль целиком
уходит в каждый запрос; сценарий — нет, в промпт идёт только описание текущего
шага. Положить сценарии в профиль значило бы платить токенами за конфигурацию,
которая модели не нужна.

## Одно описание предпочтения на три применения

`agent/preferences.py:FIELDS` — единственный источник правды. Из него собираются:

* вопросы мастера настройки (`interview.questions()`);
* строки блока «настройки пользователя» в промпте (`preferences.describe()`);
* проверка готового ответа (`PreferenceChecker`).

Добавили поле — вопрос, строка промпта и проверка появились сами. Если бы эти
три списка жили порознь, они разъехались бы на первой же правке, и агент
спрашивал бы одно, обещал другое, а проверял третье.

## Две проверки разной силы

| | инвариант | предпочтение |
|---|---|---|
| чей | проекта | пользователя |
| где описан | `profile.json`, раздел `инварианты` | `profile.json`, разделы `обращение` и `формат` |
| чем проверяется | `StateValidator` — поиск по тексту | `PreferenceChecker` — счёт слов, блоки кода, формы обращения |
| что при нарушении | повтор, затем эскалация модели, затем отказ | повтор на **той же** модели |
| если не исправлено | ответ помечен `blocked` | ответ отдаётся с пометкой о расхождении |

Эскалация на платную модель из-за предпочтения не делается намеренно: ответ на
двадцать слов длиннее просимого не стоит того, чтобы платить за него вчетверо.

## Исполнение сценария

1. `ScenarioStore.match(query)` — есть ли сценарий с подходящим триггером.
2. `Scenario.validate()` — проверка **до** первого вызова модели: имена шагов не
   повторяются, роли и стадии существуют, маршрут по стадиям проходит по
   разрешённым переходам конечного автомата. Сценарий, который сломался бы на
   середине, должен отваливаться до того, как потратил токены.
3. `ScenarioRunner.run()` — для каждого шага: перевод задачи на его стадию,
   сборка входа из названных источников, вызов модели его роли, запись
   результата в рабочую память.
4. Завершение: задача доводится до `done` и сворачивается в журнал решений.

**Настройки пользователя применяются только к последнему шагу.** Промежуточные
результаты читает следующий агент, а не человек: требовать от аналитика «кратко,
на ты, по имени» значит отнять у архитектора половину входных данных ради
вежливости, которую никто не увидит.

## Расширение

* **Новое предпочтение** — запись в `FIELDS`. Если его можно измерить, добавьте
  `check` и метод `_проверить_<код>` в `PreferenceChecker`; если нет — оставьте
  только `to_prompt`, и это честнее, чем непроверяемое обещание.
* **Новый сценарий** — запись в `scenarios.json` пользователя либо в
  `seed.SCENARIOS`. Роли моделей берутся из `catalog.ROLES`.
* **Новый слой памяти** — модуль в `agent/memory/`, поле в `MemoryManager`, блок
  в `PromptBuilder` с обязательным `why`, строка в `POLICY` для каждой стадии.
* **Новый MCP-сервер** — запись в `mcp-servers.json` в формате `mcpServers`;
  секреты — ссылками `${ИМЯ}` на `.env`, фильтр — полями `разрешить` /
  `запретить`. Код менять не нужно.
* **Новый инструмент своего сервера** — функция с `@сервер.tool(annotations=…)`
  в `mcp_server.py`; схему входа SDK строит по аннотациям типов, описания
  параметров — через `Annotated[..., Field(description=…)]`. Ожидаемые ошибки
  аргументов — `ToolError`, иначе модель увидит только «Error executing tool».
